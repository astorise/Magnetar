## ADDED Requirements

### Requirement: Exact verification of draft tokens

When speculation is enabled for a request, the Runtime SHALL verify draft tokens by running the target model once over the last committed token and up to `k` draft tokens, SHALL accept the longest prefix of drafts the target's own selection agrees with, and SHALL append the target's selection at the first disagreement (or after the last accepted draft). Under greedy selection the generated tokens SHALL be identical to target-only generation. Under stochastic sampling the Runtime SHALL use rejection sampling that preserves the target's output distribution, or SHALL NOT speculate.

#### Scenario: Greedy speculation matches target-only output

- **GIVEN** a request with greedy selection and speculation enabled
- **WHEN** it generates the same number of tokens as a target-only run of the same prompt
- **THEN** the two token sequences are identical, whatever drafts were proposed or accepted

#### Scenario: All drafts rejected

- **WHEN** the target disagrees with the first draft token
- **THEN** exactly one token, the target's own selection, is generated by that step

### Requirement: Only accepted tokens reach committed KV

KV rows written for draft tokens SHALL become committed only for accepted tokens and the target's correction. Rows of rejected drafts SHALL never be visible to later steps, sessions or requests, and a failed, cancelled or timed-out verification step SHALL leave committed KV unchanged.

#### Scenario: Partial acceptance

- **WHEN** a verification step accepts two of four drafts
- **THEN** the committed KV length grows by three (two drafts and the correction), and the next step's attention covers exactly those rows

#### Scenario: Cancellation during verification

- **WHEN** a request is cancelled while a verification step runs
- **THEN** committed KV is unchanged and no draft token is reported as generated

### Requirement: Draft sources

The Runtime SHALL support draft sources behind one interface, each proposing up to `k` tokens from request-scoped inputs: an n-gram source matching the latest tokens against the request's prompt and generated tokens; a draft-model source running a second, trust-verified Model Instance that shares the target's tokenizer; and an MTP source reading candidate logits that a Model Component declares. A draft source SHALL NOT read another request's or session's tokens or state.

#### Scenario: Draft model with a different tokenizer

- **WHEN** a draft Model Instance's tokenizer differs from the target's
- **THEN** the configuration is rejected before generation with a structured unsupported error

#### Scenario: Component without MTP heads

- **WHEN** the MTP source is requested for a Model Component that declares no MTP heads
- **THEN** it is Unsupported, and target-only or other draft sources remain available

### Requirement: Speculation controls and statistics

Speculation SHALL be disabled by default and enabled per Model Instance or request with a maximum draft length. The Runtime MAY shorten the draft length adaptively within that bound from observed acceptance, and SHALL stop speculating for a request when its acceptance makes it slower than target-only decode. Each request SHALL report drafted, accepted and generated token counts.

#### Scenario: Disable control

- **WHEN** speculation is disabled
- **THEN** generation runs target-only, with the same output and no draft source or draft model invoked

#### Scenario: Statistics

- **WHEN** a speculative request finishes
- **THEN** its usage reports drafted and accepted token counts alongside generated tokens
