## Goals / Non-Goals

Deliver the explicitly enumerated A06, D01 outcomes through Runtime telemetry; Provider timing; offline analysis tools, preserving existing trust, resolution, lifetime and portable Component contracts. Reuse the baseline contracts linked from proposal.md. Broader roadmap work is split into independent changes; adopting an inspiration project or copying its implementation is not a goal.

## Decisions

### Implementation boundary and data flow

Correlate phases with opaque local identifiers and explicit clock domains. Separate overlapping host and Device durations. Export opt-in redacted access sequences for an offline cache simulator; an offline optimum is an oracle bound, never an online policy.

### Initial implemented profile (A06)

The first increment attributes generation-step host time; D01 is not started.

- `magnetar-runtime::phase_attribution` owns a Runtime-held `PhaseLedger`, disabled by default (`ProductionLoadedModel::enable_phase_attribution` / `disable_phase_attribution` / `take_phase_attribution`). Disabled, each leaf costs one branch and records nothing.
- The generation loop opens one record per prefill or decode step and closes it before the streaming consumer runs, so consumer time is never attributed to the Runtime. Leaves are timed on the host monotonic clock and never nest: graph build through the model Component, Model Instance check, KV state preparation, graph input upload, per-node input resolution, per-node Kernel dispatch by operator, KV append, pending KV write, explicit edge write, output materialization, logits extraction, pending KV store, logits observation, sampling and commit. Wall time no leaf covers is reported as `unattributed`, so the leaves plus `unattributed` equal the step's wall time exactly, with no double counting.
- Device time and host/Device overlap are reported as `unavailable`: no Provider exposes Device timestamps yet, and host time of a leaf that waits on the Device includes that wait.
- Records carry a closed vocabulary only: phase names, operator labels from a fixed list (any other operator name becomes `other`), counts, durations and a ledger-local ordinal. No request, session, cache, resource or node identifier, token, tensor value, prompt text or path can reach a record. The ledger keeps at most 4096 steps and counts the ones it drops.
- The diagnostic `real_checkpoint_decode_cost_profile` enables the ledger after warmup and reports host time per decode step by phase, locally and in GPU CI.

### First finding: per-node plan revalidation

The first attribution of a real Qwen2.5-0.5B decode step on Reference CPU showed every node dispatch paying about 5 ms regardless of its work: a one-row `add` cost as much as a projection. `PreparedExecutionPlanExecutor::prepare_node_execution` recomputed the semantic fingerprint of the whole graph (every node, edge and attribute formatted into one string) for every node it validated, so each step fingerprinted its ~460-node graph ~460 times. The check is unchanged, but the fingerprint is now computed once per graph execution (`FingerprintedGraph`) and every node is still validated against the plan with it. On Reference CPU, a small operator's dispatch dropped from ~5.4 ms to ~0.2 ms and decode TPOT from 9.2 s to 6.6 s; most of what remains there is Reference CPU copying weights per node, which device-resident Providers do not do.

On CUDA (RTX 3060, driver 595.71.05, run 41088755268, same checkpoint, 32-token campaign on one resident instance), decode TPOT went from 1310-1342 ms (run 41051599580) to a 135 ms median (126-143 ms over five requests), warm TTFT from a 2488 ms to a 1244 ms median, and decode throughput from 0.75 to 7.4 tok/s; per-token latency growth stays near zero (0.0-0.4 ms/token). The 64-token profile now attributes a 129 ms decode step as follows: Component graph rebuild 34 ms (27%), unattributed 33 ms (25%; the loop's observation publishing and evidence formatting are not timed by any leaf yet), all node dispatches about 50 ms, output materialization 5 ms. About 1.1 s of each request's TTFT is spent outside Runtime steps (per-request plan preparation). These three are the next targets; none of them is a Kernel.

### Second finding: per-binding plan fingerprinting

Attribution was extended to request preparation (`StepKind::RequestPreparation`: session, tokenization, graph build, plan preparation, request validation). On Reference CPU with the real checkpoint, preparing a request took 1.67 s, 97% of it in plan preparation: `PreparedExecutionPlan::add_node_binding` recomputed the plan fingerprint over every binding added so far, so a ~460-binding plan fingerprinted its bindings ~460 times. `add_node_bindings` validates every binding first, adds them all and fingerprints once; the resulting plan is identical to adding them one by one. Plan preparation dropped from 1615 ms to 44 ms per request.

After both fixes (run 41100147352) an 88 ms CUDA decode step splits into about 47 ms of node dispatches (matmul 16 ms), 27 ms unattributed (30%), 5 ms KV append, 5 ms output materialization, 3 ms sampling. The unattributed share is work no leaf timed yet. Timing it on Reference CPU with the real checkpoint (leaves may now nest: each records only its exclusive time) shows about half is publishing the step's observations (per-node causal events, KV commits, token events: ~11 ms per step) and the rest the per-node loop between leaves; inside each dispatch, the Operator catalog was rebuilt for every node (~18 ms per step) and is now built once per process.

With dispatch internals attributed on CUDA (run 41127841705), the Operator catalog fix took a decode step from 88 ms to 79 ms (campaign: TPOT median 102 -> 84 ms, warm TTFT median 128 -> 104 ms, 11.9 tok/s). The step then split into 16 ms unattributed, 15 ms publishing observations, 14 ms of dispatch bookkeeping, 9 ms Kernel submission (asynchronous), 7 ms edge writes, 5 ms output materialization (which waits for the Device) and 4 ms Kernel resolution. Publishing was slow because `InferenceApiObserver` kept its last 4096 observations by removing the first element of a `Vec` for every new one once full: about 2300 observations per step each shifted ~4096 entries. It now drops the oldest half in one batch when the buffer reaches twice its capacity and exposes only the most recent 4096, so recording is amortized O(1); on Reference CPU publishing went from 10.9 to 1.8 ms per step. Two more leaves (`graph_prepare`: per-step execution order, Provider and weight bindings; `node_output_bind`) cut the CPU's unattributed time from 10.5 to 3.9 ms per step.

CUDA run 41131032958 confirmed it: the decode step dropped from 79 to 64 ms and observation publishing from 15 to 1.3 ms; campaign TPOT median 84 -> 72 ms, warm TTFT median 103 ms, 13.8 tok/s. Per-step graph preparation then cost 10 ms: the execution order was computed by repeatedly scanning every remaining node for the first ready one, O(nodes^2). Kahn's algorithm taking the smallest ready id produces exactly the same order in O(edges log nodes) (checked against the previous algorithm, including cycle rejection); on Reference CPU graph preparation went from 4.9 to 0.8 ms per step.

CUDA run 41133684237: decode step 64 -> 54 ms, graph preparation 10 -> 0.8 ms; campaign TPOT median 72 -> 63 ms, warm TTFT median 94 ms, 15.9 tok/s. The largest remaining host cost was 13.7 ms of exclusive dispatch work: each node looked up its plan binding with four linear scans of the ~460 bindings (affinity, memory class, output placement, plan validation). `PreparedExecutionPlan::node_binding` answers from a lazily built index that the binding methods reset and that falls back to a scan whenever it might be stale; on Reference CPU exclusive dispatch work went from 50.7 to 43.5 ms per step, most of the rest being Reference CPU's own host copies. Edge writes are now labelled by operator to identify the 24 per step CUDA still performs.

CUDA run 41136603791: exclusive dispatch work 13.7 -> 10.3 ms, Kernel resolution 4.0 -> 3.1 ms; campaign TPOT median 61.5 ms, warm TTFT median 96 ms, 16.3 tok/s. The operator-labelled edge writes were all 24 `rope` nodes per step (10 ms): RoPE never received an output target, so the query rotation (`rope_q`, no KV semantics) was downloaded to the host and uploaded back into its edge after every dispatch, each download synchronizing the Device. Only a RoPE output carrying KV-cache semantics (`rope_k`, appended to the history by the graph executor) still goes without a target; `rope_q` writes straight into its edge. The real checkpoint still matches the independent corpus on Reference CPU (max |logit diff| 5.4e-5, same 16 tokens).

CUDA run 41139290311 (logits still within 6.6e-5 of the corpus, same tokens): the decode step went from 53 to 49 ms and the edge writes disappeared; campaign TPOT median 61.5 -> 56.8 ms, warm TTFT median 91 ms, 17.6 tok/s. Output materialization then led with 11 ms: every step downloaded every live edge of the graph (~460 tensors, KV history included) although generation only reads the logits. The generation hot path now downloads only `logits`; conformance and test entry points that inspect intermediate edges still download all of them. Reference CPU still matches the corpus (5.4e-5, same tokens).

CUDA run 41141782776 (logits still within 6.6e-5 of the corpus): decode step 49 -> 45 ms, campaign TPOT median 53.0 ms, warm TTFT median 83 ms, 18.9 tok/s. Output materialization (8.7 ms) is now a single logits download that waits for the step's queued Device work. What remains is per-dispatch host work spread over ~460 nodes: about 10 ms of dispatch bookkeeping, 9 ms of Kernel submission and 3 ms of Kernel resolution, i.e. roughly 50 us of host time per node. Removing it is a matter of dispatching fewer, larger units (fusion, `qualify-fusion-and-optimized-attention`) or replaying a captured step (`capture-and-replay-cuda-graphs`) rather than of another local fix.

Part of that per-node host work was still quadratic: every allocation (one per node output, ~460 per step) summed the bytes of every live allocation (~800: weights, edges, KV) several times for admission and pressure, and scanned them all again for a reusable one. `MemoryManager` now keeps those totals by state, class and pinned placement up to date at the four places its allocation table changes, and skips the reuse scan when nothing is cached; tests recompute the totals after every operation and after every request of a resident model. On Reference CPU exclusive dispatch work went from 43.5 to 36.2 ms per step and edge writes from 7.5 to 1.4 ms.

CUDA run 41173281286 (after the MemoryManager totals fix): exclusive dispatch work 10.2 -> 6.8 ms, but campaign TPOT only 53.0 -> 52.0 ms (19.2 tok/s) while the final wait for the Device grew from 8.7 to 13.3 ms: with the host overhead gone, each step was bound by Device time, far above the ~6 ms it takes an RTX 3060 to read the model's ~2 GB of F32 weights once. The CUDA Provider's `matmul_kernel` gave each output column one thread summing all of `k` in series (a 896x896 decode projection ran on 896 threads), and `rmsnorm_kernel` one thread per row. The Provider now uses a split-K matmul (one block per row and 32-column tile, 16 warps over interleaved slices of `k`, coalesced reads, fixed-order sum) whenever `b` is not transposed, and a 256-thread block per RMSNorm row with a fixed-order tree reduction. Run 41174709795 (Provider conformance tests on the device, including the new uneven-shape ones): decode step 44 -> 33 ms, final Device wait 13.3 -> 1.8 ms, campaign TPOT median 52.0 -> 38.9 ms, warm TTFT median 77 ms, 25.7 tok/s; logits within 2.0e-5 of the independent corpus (was 6.6e-5), same tokens. The step is host-bound again: ~8 ms Kernel submission, ~7 ms dispatch bookkeeping, ~3 ms Kernel resolution per step.

Every executor (Reference CPU, the CPU and the CUDA Provider) also appended two Kernel observations per dispatch to a log it never trimmed: ~900 entries per decode step for as long as a resident model served. Each now keeps the most recent 4096, dropping the oldest half at twice that (run 41187919173, re-run after a runner pod failure: decode step unchanged at 33.6 ms, campaign TPOT median 36.8 ms). Kernel submission on CUDA then cost 8.5 ms per step, largely driver calls around each Kernel's fresh output allocation: cudarc created and destroyed two events per allocation although it only synchronizes through them once a context has a second stream, which this Provider never creates, and every output was zeroed before Kernels that overwrite all of it. With event tracking off and those outputs allocated uninitialized (run 41189317282, logits still within 2.0e-5 of the corpus): Kernel submission 8.5 -> 6.5 ms, decode step 33.6 -> 30.1 ms, campaign TPOT median 34.8 ms, warm TTFT median 65 ms, 28.7 tok/s.

With the fusions (`cache-and-optimize-prepared-graphs`, run 41206197579: 315 dispatches, decode step 25.2 ms, campaign TPOT median 31.2 ms) the step was still mostly host work around each node. Profiling the Runtime's own dispatch path under callgrind (canonical fixture on Reference CPU, whose Runtime-side path is the one CUDA takes) found, per step: the graph's plan fingerprint (SHA-256 over its canonical text) and execution order recomputed for a graph the cache never changes; greedy sampling taking every `exp` twice over the 151936 logits and building two vocabulary-sized vectors, with every candidate looked up in every token-mask set; the logits copied before sampling; four allocations per published per-node observation. Per node: the selected Kernel advertisement copied out of the registry, the selection request's bindings copied twice into the dispatch plan, a revalidation observation formatted for a dispatcher dropped right after, and an allocated key string for every registry lookup. The fingerprint and order are now memoized with the cached graph (`GraphExecutionMemo`), greedy selection computes the same maximum, ranking and probability (bit-identical, tested against the softmax path) in one pass and only takes the `exp` sum when probabilities are reported, token masks mark their own candidates, logits are moved into sampling, observations are built with one `format!` (same text), and dispatch borrows the advertisement alongside the Memory Manager and phase ledger (`Runtime::kernel_registry_memory_and_phases_mut`), builds its plan from the request by value, skips the unread observation and looks Kernel keys up through a per-thread buffer. On Reference CPU with the real checkpoint (logits unchanged, 5.4e-5, same tokens): sampling 3.10 -> 0.68 ms, Kernel resolution 5.88 -> 3.84 ms, observation publishing 1.30 -> 0.73 ms, graph preparation 0.55 -> 0.10 ms, unattributed 2.71 -> 1.44 ms per step. CUDA run 41210946249 (logits within 2.0e-5 of the corpus, same tokens): decode step 25.2 -> 19.5 ms (sampling 2.52 -> 0.55, unattributed 3.01 -> 0.89, Kernel resolution 1.96 -> 1.30, observation publishing 0.98 -> 0.45 ms); campaign TPOT median 31.2 -> 25.5 ms, warm TTFT median 57.8 -> 49.3 ms, 39.3 tok/s.

Two smaller follow-ups (run 41212230026, logits within 2.0e-5 of the corpus, same tokens): the KV-history append asked the Kernel Registry the same `concat` selection for every layer's K and V (48 per step); the dispatch context now keeps the last answer together with everything it was selected for (affinity, memory class, each resource's descriptor and affinity) and reuses it on a match. The CUDA Provider's RoPE filled its output with a device copy of the input before rotating; when the rotation covers whole heads (Qwen2, Llama) the Kernel writes every element, so the copy is skipped. KV append 2.07 -> 1.81 ms, RoPE Kernel submission 1.15 -> 0.86 ms, decode step 19.5 -> 18.8 ms; campaign TPOT median 25.5 -> 25.2 ms, warm TTFT median 48.4 ms, 39.7 tok/s. The step is now split between ~9 ms of per-dispatch host work (Kernel submission 4.5 ms, dispatch bookkeeping 4.0 ms), the final wait for the Device behind the logits download (3.7 ms) and the KV append and pending copy (2.3 ms).

### Identity, eligibility and recovery

Inputs retain validated artifact/model/Component identities, dtype/layout, phase, shape and version provenance where relevant. Runtime checks trust, ResourceAffinity, capability support and MemoryManager admission before policy ranks candidates. Plans and state reference immutable generations and opaque leases. Cancellation stops future submissions; in-flight work retains its leases until completion. On Device loss or incompatible state, invalidate affected work and replan or fail explicitly; never silently rebind resources or restore an untrusted generation.

### Compatibility and WIT evolution

Preserve existing F32 and single-Device baseline fixtures and public request semantics. Reuse current WIT and Rust contracts first. Before implementation requires new graph operators, state envelopes or result types, record their exact versioned portable schema, negotiation, unsupported behavior and migration tests; native API types are prohibited. A new precision or model profile is opt-in until its validation evidence supports promotion. Vendor implementations stay in their repositories, followed by an explicit parent submodule pin update.

### Authority and isolation

Tools and service/transport adapters use caller-authorized inputs and bounded operations. Inference and Components gain no ambient filesystem, network, process, source-control or secret authority. Local source streaming checks artifact ranges and identity. External campaigns/artifacts are untrusted until verified. Snapshot or distributed data remains tenant-scoped and requires authorization in addition to checksums; signing keys and credentials never enter reports.

### Qualification and rollout

Use the shared real-checkpoint harness and baseline corpus rather than inventing isolated pass criteria. A profile records checkpoint revision/digests, code and Provider SHAs, hardware/driver, flags, dtype, shape, budgets and warmup. Exercise 1/4/16/32 sessions, 512/4096/16384-token contexts and 128-512 generated tokens only inside model/backend/capacity limits; report every skipped combination. Repeat at least five warm runs when affordable and document exceptions, uncertainty and cold costs. Check logits and downstream quality with declared thresholds; token identity alone is insufficient. Measure TTFT, TPOT/ITL p50/p95/p99, aggregate/per-request throughput, launch/phase/copy/I/O costs, RSS/VRAM, fragmentation, useful cache savings and energy only when valid telemetry exists.

Promotion requires appropriate real hardware and a real checkpoint, error/cancellation/memory-pressure/isolation tests, before/after evidence, a disable control and a qualified fallback or structured Unsupported result. Experimental features remain disabled by default until qualified. Run existing Rust, WIT, OpenSpec, license/SBOM/signature and artifact-reproducibility gates for affected code. Compare tail latency and total memory as well as throughput, under the same budget. Publish limitations and do not infer a blanket speedup from heterogeneous runs.

## Risks / Trade-offs

- Trace collection must not leak prompts, tensor values, weights, secret paths or cross-tenant access patterns.
- A performance win can be below measurement noise or transfer cost; stop promotion until evidence meets the declared objective and uncertainty threshold.
- Wider hardware coverage is constrained by actual machines; record missing hardware as skipped, not passed, and deliver at most a contract or POC for that target.

## Migration and rollback

Land compatibility scaffolding and baseline tests before optimized execution. Keep new paths selectable and disableable by profile. Drain or fence old generations at safe boundaries; in-flight references remain alive. Roll back only to a still-trusted, resource-compatible qualified generation. If no safe fallback exists, return a structured error. Document any public schema migration before implementation and preserve supported old readers/linkers during the declared compatibility window.

## Open questions

Select exact hardware/checkpoint, numerical and downstream-quality thresholds, resource budgets and SLOs per qualification profile before promoting it. The roadmap's reference CPU/CUDA and Qwen checkpoint are the initial comparison, not evidence that other targets are available. Any Tachyon-facing interface additionally needs its independent repository audit and owner agreement. These decisions gate implementation promotion, not creation of this proposal.
