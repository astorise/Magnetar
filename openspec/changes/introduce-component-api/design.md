## Context

### Where the contract is today

- The source is `magnetar-runtime/wit/model-component-graph.wit`, at 1.14.0, 619 lines, one package with two interfaces (`graph-builder`, `model-config`) and two worlds (`model-component-graph-producer`, `encoder-component-graph-producer`).
- Eight Components carry a copy, at the versions in the proposal; Qwen's is byte-identical to the Runtime's, and so is ModernBERT's to the Runtime's 1.12.0.
- The Runtime serves the contract from 1.2.0 on (the `model-component-graph-contract` spec's "Earlier contract versions keep linking"), but holds only the current file: the files of 1.2.0 to 1.13.0 exist only in Git history, some of them only in the branch of a squash-merged pull request.

### What the history says about the contract's discipline

Between the thirteen versions 1.2.0 to 1.14.0, no interface, function or type is removed, and no signature or existing member changes. The only changes that are not pure additions are two cases appended to the end of a type: `yarn` on `rope-frequency-scaling` (1.7.0) and `encode` on `graph-phase` (1.12.0). The additive rule is real; nothing but review enforced it.

### What was tried

A copy of the Mistral Component, moved onto a first version of the crate (contract 1.8.0, bindings generated by the crate, no `wit/` copy, no generator call): its 13 tests pass, the seven golden graphs recorded before the move among them (so the graphs it emits are unchanged), its `.wasm` validates as a Component, and the interface of that `.wasm` is the one the Component builds from its own copy of the WIT (the same declarations, in a different order). The `.wasm` is 125,217 bytes against 122,630 (+2.1 %).

Trying it also found a constraint: generating two versions in one crate fails, because the export macro a library has to make public is a crate-level macro named after the world, and the world has the same name in every version. See D2.

## Goals / Non-Goals

**Goals**
- A Component's author reads and targets the contract without a checkout of Magnetar, and cannot target a file that is not a released version.
- A released version never changes, and a release that is not additive cannot land.
- The bindings are generated in one place, once per version.
- Moving a Component onto the crate changes nothing it emits.

**Non-Goals**
- Changing the contract. Every file here is a version that already exists.
- Typed operator constructors. They need the operator catalog to be readable outside the core (it lives in `magnetar-core`), which is the SDK follow-up on operators a Component brings; this change leaves the contract's operator names as strings, as they are.
- A guest-side crate in a language other than Rust. The WIT is language-neutral and is what other languages generate from; their bindings are theirs.
- Making the Runtime take the contract from the repository in this change (D6).

## Decisions

### D1. One home, one directory per version, immutable

`wit/<version>/model-component-graph.wit` for each released version, `wit/SHA256SUMS` recording them, `wit/PROVENANCE.md` saying which Magnetar commit each came from and which Component copies confirm it. A released file never changes: the tests compare it with its record, and CI refuses a pull request that edits or removes a file of a released version or a recorded checksum. A new version is a new directory, and `scripts/sync.py` derives the checksum line, the cargo feature and the bindings module from the directories, so that releasing is adding a file and running one command.

Versions 1.0.0 and 1.1.0 are not carried: the Runtime serves 1.2.0 and later. Thirteen versions are, five of them confirmed byte for byte by a Component's copy, 1.11.0 by being the file 1.12.0 was written from.

### D2. Bindings generated once, one cargo feature per version, exactly one per build

The crate generates a version's guest bindings in the module of the matching feature (`v1_14`), with the generator's public export option so that a Component calls the crate's `export!`. A Component enables the feature of the version it targets.

The generated export macros are crate-level macros named after the world, the same in every version, so two versions cannot live in one crate: enabling two features is refused with a message that says so, rather than with the generator's two dozen duplicate-definition errors. A build targets one version of the contract, and a Component has one. The consequence is that Cargo's feature unification joins the Components of one workspace that target different versions into one build; Components live in their own repositories, each its own workspace, so the case does not arise today, and it is stated in the crate's documentation.

The alternative is one crate per version (`magnetar-component-api-v1_14`), which removes the limit and costs thirteen packages to publish and keep in step. It stays available if the limit bites.

### D3. The dependency runs one way, and the SDK stays free of it

Runtime and Components both depend on the contract; the contract depends on neither. The SDK does not depend on the API: `wit_graph_sink!` takes the `gb` alias the Component names, which can be its own generated module or the API's, since the macro relies only on the `graph-builder` items present since 1.8.0. A Component that uses both writes one line to connect them, and the SDK keeps no dependency and no feature tied to a contract version.

### D4. Additivity is checked on the WIT

For every pair of consecutive versions, the test parses both and refuses: a removed interface, function or type; a changed function signature; a type that changes kind; a record, an enum, a variant or a flags type that changes or reorders an existing member; and a record or flags type that grows. A variant or an enum may gain cases at its end, which is the one growth the contract allows: the Runtime encodes each value against the calling Component's own types, so a Component built before the case fails its call instead of receiving a case it cannot represent. Negative tests build the pairs that break each rule and check that they are found.

Run over the thirteen real versions it finds nothing but the two appended cases above.

### D5. Pinned git dependency, then crates.io

As for the SDK (its D4): a Component's repository runs its own checks without a Magnetar checkout, so it depends on the crate by commit, its `Cargo.lock` records it, a branch or a tag is refused, and the crate is published once the contract's tooling has been through the Components. The cargo features are the same on crates.io.

### D6. How the Runtime takes the contract from here (open)

The Runtime needs the WIT files to generate its host side. Two ways, to be decided when the first Component has moved, with its own delta to `wit` and `model-component-graph-contract`:

1. **A submodule** `contracts/component-api` pinned by commit, with the Runtime's `bindgen!` paths pointing into it and `magnetar-runtime/wit/` removed.
2. **The Runtime's copy stays** and a Magnetar CI test compares it with the repository's file of the same version (byte for byte), so that the Runtime cannot drift.

Until then nothing in Magnetar changes: task 3.1 adds the comparison (option 2) as a safety net that holds in either case.

### D7. Adoption is a design input

`examples/minimal-component` is the whole surface of a Component, 60 lines, built and validated as a Component in CI. The README leads with what a Component's `Cargo.toml` and entry point look like. A `cargo generate` template and typed operator constructors are the next steps for a third party, and both are follow-ups (the second depends on the operator catalog, see Non-Goals).

## Risks / Trade-offs

- **One version per build.** D2. Stated, tested, and with an escape (a crate per version).
- **The repository becomes a gate for contract changes.** It is meant to: a version is added there first. Review of a new version is review of one WIT file with the additive check green.
- **The Runtime drifts from the repository** until D6 is settled. The comparison test of task 3.1 closes it.
- **A Component's `.wasm` grows by about 2 %** (measured on Mistral). It is the cost of the crate's two component-type sections; the crate does not change what a Component emits or how the Runtime executes it, so it is not an inference-speed change.
- **Recovered versions.** Some versions only ever existed in pull request branches. They were cross-checked (D1), and a version that cannot be cross-checked is not carried.
