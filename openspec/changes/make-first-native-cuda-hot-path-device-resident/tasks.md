**Critical bug found and fixed during 3.14's regression pass, not by inspection but by a real end-to-end oracle divergence**: `magnetar-runtime/src/reference_cpu.rs` carries its own in-crate copy of `rope()` (the "in-crate test double" the module's own doc comment describes, independent from `providers/cpu`'s copy) -- and its "rope" Kernel dispatch arm is what `ReferenceCpuExecutor` (the executor `dispatch_qwen_graph_node` and every oracle actually dispatch through) runs. Tasks 3.4-3.9 above updated `providers/cpu` and `providers/cuda`'s copies and dispatch arms, but missed this third copy entirely -- it kept its old 5-argument signature and silently ignored the new `head_count` attribute, rotating only the first `dimension` columns of every row regardless of `head_count`, leaving every head beyond the first completely unrotated. This produced identical (but wrong) results whether compared through `dispatch_qwen_graph_node` (the graph) or through the oracle functions this task group also updated to call the same shared `dispatch_qwen_rope` -- both shared the same silent bug, so they agreed with each other while disagreeing with `e2e_forward_hidden_states`'s fully independent, hand-written reference implementation (`apply_rope_per_head`, deliberately left untouched), which is what caught it. Fixed by applying the identical `head_count`/`head_width` correction to `reference_cpu.rs`'s own `rope()` and its dispatch arm, plus the same new multi-head/partial/GQA test trio in `reference_cpu/tests.rs`. This is the exact class of gap task group 7's end-to-end hardware test exists to catch -- confirmed here at the Reference CPU level before ever reaching real CUDA hardware.

## 6. Pre-admission rollback: a real transactional guarantee (design.md Decision 7)

- [x] 6.1 Red test baseline: before this fix, `resolve_output_target` admitted a caller's output unconditionally via `admit_kernel_output`, and neither it nor any of the leaf `dispatch_qwen_*` functions released that admission if the subsequent `dispatch_reference_cpu_operator` call failed for any reason -- confirmed by reading every call site (`resolve_output_target`'s own doc comment, pre-fix, documented no rollback of its own). Fix: new `rollback_pre_admitted_output` (releases the `TensorResidency` and its Memory Manager allocation, best-effort) plus a new consolidated wrapper `dispatch_reference_cpu_operator_pre_admitted` (pre-admits via `resolve_output_target`, dispatches, rolls back on any `Err`) replacing the old `resolve_output_target` + `dispatch_reference_cpu_operator` two-step pattern at all 7 call sites (`dispatch_qwen_matmul`, `dispatch_qwen_unary`, `dispatch_qwen_binary_same_shape`, `dispatch_qwen_rmsnorm`, `dispatch_qwen_rope`, `dispatch_qwen_attention`, and the "embedding" match arm inline in `dispatch_qwen_graph_node`).
- [x] 6.2 Rollback on submit-time failure: new test `e2e_graph_dispatch_rolls_back_pre_admitted_output_on_submit_time_failure` reuses the existing tight-Runtime-memory-budget scenario (`attention`'s required workspace failing to admit -- a genuine Kernel Registry/dispatch-plan-construction-adjacent failure, since workspace allocation never even creates an allocation object on failure) and additionally asserts the failing node's own pre-admitted output allocation (the highest-id allocation at that point, mirroring `stage_weight_propagates_and_rolls_back_on_provider_write_failure`'s existing reasoning) ends in `Released` state, not leaked as `Active`.
- [x] 6.3 Rollback on kernel/completion-time failure: new mock `KernelFailableProviderExecutionApi` (wraps a real `ReferenceCpuExecutor`, injects a `complete_kernel` failure for one targeted Operator by name, delegates everything else including weight materialization untouched) plus `TestFailableKernelProvider` (a full `Provider` -- `devices()`/`kernel_advertisements()` included, unlike the narrower `TestFailableProvider` -- needed since this test drives real Kernel-Registry-backed graph dispatch, not just weight materialization). New test `e2e_graph_dispatch_rolls_back_pre_admitted_output_on_kernel_completion_failure` targets `embedding` (the first node this fixture's prefill graph dispatches, so zero earlier nodes have admitted anything of their own) and asserts the Runtime's Active allocation count after the failed dispatch is exactly one higher than right after model loading -- the "+1" being the graph's own `input.token_ids` resource, admitted up front before any node dispatches and legitimately never rolled back.
- [x] 6.4 Both Memory Manager and Provider storage are exercised by 6.2/6.3: 6.2's assertion reads `MemoryManager::allocations()` state directly; 6.3's mock additionally proves the Provider-side handle bookkeeping (`failing_handles`) never falsely believes a rolled-back dispatch's Kernel work is still outstanding -- a cleared `fail_operator`/`failing_handles` retry (see 6.5) would itself fail if Provider-side state were left inconsistent by the rollback.
- [x] 6.5 Final test: 6.3's test additionally retries the identical dispatch (fresh `KvCacheId`, injected failure cleared) immediately after the rolled-back failure and asserts it now succeeds cleanly -- proving no orphaned allocation or stale `TensorResidency` under the same resource id survives to collide with or corrupt a subsequent legitimate dispatch.
