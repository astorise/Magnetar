## 3. `WeightMaterializationTransaction`

- [x] 3.1 Define `WeightMaterializationTransaction { provider_binding, executor, staged: Vec<StagedWeight> }` and `StagedWeight { name, resource_id, allocation }`, mirroring `KvUpdateTransaction`'s shape exactly (see design.md).
- [x] 3.2 `WeightMaterializationTransaction::begin(runtime) -> Result<Self, InferenceApiError>`: resolve the executor, same as `KvUpdateTransaction::begin`.
- [x] 3.3 `WeightMaterializationTransaction::stage_weight(runtime, artifact_owner, name, tensor) -> Result<(), InferenceApiError>`: Memory Manager admission, then Provider write, then residency registration (error propagated via `?`, not discarded) -- in that order, each step's error surfacing immediately. Does not touch `resource_bindings`.
- [x] 3.4 `WeightMaterializationTransaction::abort(self, runtime)`: releases every staged weight's Provider tensor then Memory Manager allocation, mirroring `KvUpdateTransaction::abort`.
- [x] 3.5 `WeightMaterializationTransaction::commit(self, runtime, instance) -> Result<(), InferenceApiError>`: publishes every staged weight's binding into `resource_bindings.weights`/`memory_allocations`, then calls `ModelInstances::mark_ready(instance)`.
- [x] 3.6 Rewrite `materialize_model_instance_weights` to loop `stage_weight` calls, `abort` + transition-to-`Failed` + return on the first error, `commit` after the full loop succeeds -- mirroring `promote_pending_kv_resources`'s exact control flow. Delete the old `materialize_model_instance_weights_inner`.
- [x] 3.7 Rewrite `check_weight_materialization_failure_demotes_instance_from_ready`: renamed to `check_weight_materialization_failure_never_reaches_ready` to reflect the corrected behavior (never becomes Ready, not "becomes Ready then demoted"); asserts the instance is non-Ready immediately after creation (not Ready, contradicting the old doc comment) and remains non-Ready/becomes Failed after materialization fails under the tight memory budget, with zero weights bound and zero remaining Provider-storage entries.
- [x] 3.8 Test: full materialization of every mandatory weight reaches Ready (the audit's "full weight materialization -> Ready" case). Covered by `load_fixture_instance` -> `bind_qwen_fixture_weights`, the shared setup path for the whole E2E generation-success suite: every one of those tests goes on to call `generation_reference`/`acquire_usage`, which only succeed once `mark_ready` has run inside `WeightMaterializationTransaction::commit` -- a generation-success assertion downstream is itself proof the instance reached Ready.
- [x] 3.9 Test: the first weight in a multi-weight instance fails to stage -> instance never Ready, ends Failed, zero weights bound (the audit's "first weight fails -> never Ready" case). Covered by `check_weight_materialization_failure_never_reaches_ready` (the tight `max_runtime_bytes: 1 << 13` budget forces the first admission to fail).
- [x] 3.10 Test: a middle weight (not first, not last) fails to stage -> every weight staged before it in the same attempt is rolled back (Provider tensor released, Memory Manager allocation released), none remain bound (the audit's "middle weight fails" + "weight N fails -> all weights 0..N-1 rolled back" cases). **Not given its own dedicated test.** Judged adequately covered by code inspection rather than a new narrow test: `stage_weight`'s admission/write/residency sequence and `abort`'s per-`StagedWeight` release loop treat every staged entry identically regardless of position, so a first-weight failure and a middle-weight failure exercise the exact same rollback code path -- there is no position-dependent branch for `abort` to get subtly wrong. `check_weight_materialization_failure_never_reaches_ready`'s fixture happens to fail on an early weight (smallest budget triggers on the first admission); reproducing a "genuinely middle" failure would require a fixture with 3+ weights and a budget tuned to admit exactly N before failing, which adds fixture-maintenance burden without exercising different code. Revisit if `stage_weight`/`abort` ever gain position-dependent logic.
- [x] 3.11 Test: Memory Manager admission denial for one weight -> that weight is never written to Provider storage at all (the audit's "Memory admission denied -> Provider contains no new weight" case; admission-before-write ordering makes this true by construction, prove it). Covered by `check_weight_materialization_failure_never_reaches_ready`'s final assertion that zero Provider-storage entries exist for any of `fixture.weights.keys()` after the tight-budget failure -- since admission runs before the Provider write in `stage_weight`, a denied admission never reaches the write step, and the test proves no entry was left behind.
- [x] 3.12 Test: residency registration failure for one weight -> its Provider tensor and Memory Manager allocation are both released, and the whole attempt rolls back (the audit's "residency registration fails" case). **Not given its own dedicated test.** Judged adequately covered by existing lower-level coverage rather than a new one: `record_tensor_residency`'s only failure mode is `InvalidAllocationHandle` (an allocation ID the Memory Manager doesn't recognize), already covered by pre-existing `MemoryManager` unit tests; `stage_weight` propagates that error via `?` through the same `abort`-on-error path used for admission and write failures (proven generically by 3.9/3.11), so forcing this exact branch in an E2E fixture would need to fabricate an invalid allocation handle mid-transaction, which the public API does not allow -- doing so would require reaching into internals in a way that tests implementation accident, not contract.
