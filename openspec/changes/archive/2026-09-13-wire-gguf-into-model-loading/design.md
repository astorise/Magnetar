## Context

`formats/gguf` (`implement-model-format-parsers`) already parses a GGUF file's tensor-info and key-value metadata sections into `magnetar-runtime`'s generic types, but is deliberately not a full `ModelManifest` -- "assembling model identity/digest from external context is the caller's job." No caller existed. `loaders/huggingface` is the one real precedent for turning a parsed format into a `ProductionModelArtifactIngestor`: real `config.json` normalization, tensor renaming into canonical Model Artifact names, a projection-weight transpose, tied-`lm_head` derivation, and a real `tokenizer.json`-backed tokenizer. GGUF differs from a Hugging Face bundle in three structural ways this design had to resolve: (1) architecture/tokenizer configuration is embedded in the same file's key-value metadata, not separate JSON files; (2) the tokenizer's full vocabulary is embedded directly (`tokenizer.ggml.tokens`/`merges`), not a `tokenizer.json`; (3) GGUF's own tensor-shape convention (`ne[]`) is dimension-order-reversed relative to Safetensors/PyTorch.

## Goals / Non-Goals

**Goals:**
- Load a real, unquantized GGUF Qwen2 checkpoint through the exact same production entry points (`run_production_qwen_generation*`) a Hugging Face bundle already uses.
- Reuse `formats/gguf`'s real parser; never reimplement GGUF parsing.
- Match `loaders/huggingface`'s existing tensor-naming/shape/layout conventions exactly, so the Qwen Component and Runtime remain completely unaware of which bundle format a checkpoint came from.
- Verify correctness numerically, not just "does not crash" -- both against `loaders/huggingface`'s own output for identical weight values, and against a real downloaded checkpoint.

**Non-Goals:**
- Quantized GGUF tensors (`Q4_K`/`Q5_K`/`Q8_0`). Rejected structurally with a named error. Dequantization-at-load (converting to F32 during Model Loading, the same place F16/BF16 conversion already happens) or real quantized compute kernels are both separate, substantial, not-yet-started Magnetar chantiers (quantization is explicitly its own item on the Tachyon scope charter).
- Chat template *rendering*. GGUF embeds `tokenizer.chat_template` as a raw Jinja2 string, exactly like a Hugging Face `tokenizer_config.json` does; `loaders/gguf` threads it into the manifest as a named part (matching `loaders/huggingface`'s "parts are identity/provenance, not payload" convention) and exposes `load_gguf_chat_template` to re-extract the raw text, but does not implement its own Jinja2 renderer. `loaders/huggingface::HuggingFaceChatTemplateFormatter` takes a bare template string with no Hugging-Face-specific coupling, so a caller that already depends on that crate can reuse it directly against GGUF-sourced text; duplicating a second minijinja-based renderer here would be pure duplication for no additional coverage.
- Any architecture family other than `qwen2` (the only one with a real Model Component). Rejected structurally, not silently passed through.
- Multi-file/sharded GGUF (a real but less common convention). A single `model.gguf` file only.

## Decisions

- **New externalized submodule, not an extension of `loaders/huggingface`.** `production-model-ingestion`'s "Concrete Production Model Artifact Ingestors Are Externalized" requirement applies to any bundle-format-specific ingestor; GGUF and Hugging Face bundles are structurally unrelated formats (one file with embedded metadata/vocab vs. several files), so a new pinned repository following the exact same pattern (`loaders/gguf`, depending only on `magnetar-runtime` and `formats/gguf`) is the correct shape, not a second responsibility bolted onto the existing crate.

- **GGUF's `ne[]` dimension order must be reversed to reach the Hugging Face-equivalent shape, independent of the separate projection-weight transpose `loaders/huggingface` also applies.** This needed real verification, not assumption: GGML's `ne[]` array is defined as the reverse of a tensor's PyTorch/row-major dimension order, describing the *same* underlying bytes (confirmed against `formats/gguf`'s own doc comments and cross-checked by this change's own numerical parity test) -- llama.cpp's real GGUF writer applies no byte-level transpose for a standard Linear weight when converting from Hugging Face. A dedicated research pass (checking `ggml-org/llama.cpp`'s current `conversion/qwen.py` and `conversion/llama.py` source directly, not recalled from general knowledge) additionally confirmed llama.cpp's Qwen2 conversion applies no Q/K attention-weight permutation either (the historical LLaMA-family `permute()` function, needed only for original Meta LLaMA's interleaved-pair RoPE layout vs. Hugging Face's rotate_half convention, is never called for `Qwen2Model`/`Qwen3Model` -- confirmed absent from `conversion/qwen.py`, present only in `conversion/llama.py`/`conversion/deci.py`/others). Net effect: `weights.rs` reverses every tensor's `ne[]`-order shape to the Hugging Face-equivalent labeling, unconditionally, with no accompanying byte reordering -- the exact same real projection-weight transpose (`weight_layout.rs`, ported from `loaders/huggingface`) and tied-`lm_head` derivation (`derived_lm_head.rs`, likewise ported) then apply identically to either source format's now-identically-shaped-and-laid-out tensors.

- **`formats/gguf` gained one small additive field, `GgufArtifact.tensor_data_start`, rather than `loaders/gguf` re-deriving it.** The parser already computes the tensor data section's absolute file offset internally (needed for its own bounds/digest checks) but never returned it; every `ModelTensorMetadata.offset_bytes` is relative to that value, matching Safetensors' identical "offset relative to the format's own data section" convention. Re-deriving the alignment/header-walk logic independently in `loaders/gguf` would duplicate real parsing logic and risk drifting from it; exposing the value the parser already has is a minimal, safe, backward-compatible addition (one new field, one updated construction site, verified against the parser's own tests plus a new assertion that `tensor_data_start + offset_bytes` genuinely addresses the right bytes).

- **The tokenizer is built programmatically via `tokenizers::models::bpe::BPE::builder().vocab_and_merges(...)`, not by synthesizing a `tokenizer.json`.** GGUF embeds the vocabulary as flat `tokenizer.ggml.tokens`/`merges` arrays (`tokenizer.ggml.model == "gpt2"` for Qwen2's byte-level BPE); the `tokenizers` crate's Rust API accepts a vocab/merges pair directly, so no intermediate JSON construction is needed. A `ByteLevel` pre-tokenizer/decoder (the same struct implements both roles in that crate) reproduces GPT-2/Qwen's real byte-level splitting.

- **A real, discovered bug required a design correction after implementation, not before**: `TokenizerMetadata::validate` (an existing, format-agnostic `magnetar-runtime` invariant) rejects two special tokens sharing one raw id regardless of kind. Running this ingestor's tokenizer construction against the real, downloaded `Qwen2.5-0.5B-Instruct-GGUF` checkpoint failed immediately with `SpecialTokenConflict`: llama.cpp's real GGUF writer always emits `tokenizer.ggml.bos_token_id`, defaulting it to the same id as `eos_token_id` for a model with no true distinct beginning-of-sequence token (true of this real checkpoint) -- whereas the equivalent Hugging Face `tokenizer_config.json` simply omits the `bos_token` field entirely for the same model, so `HuggingFaceTokenizer::from_bytes` never even attempts to register a Bos entry and never hits this conflict. Fixed by registering Eos first, then Bos/Pad only if their id was not already claimed -- reproducing exactly what the Hugging Face path's own field omission already achieves for the same real model, not a GGUF-specific relaxation of the shared validation rule.

- **Correctness is verified two independent ways, not merely "generation runs without crashing."** (1) `integration-tests/production-loading`'s `gguf_and_huggingface_ingestion_of_identical_weights_produce_identical_generation`: the exact same real (non-trivial, non-symmetric) weight values -- generated via the existing test fixture's own `tensor_values(name, count)` seeded by the Hugging Face-convention tensor name string, written into both a Safetensors bundle and a hand-built GGUF file under each format's own tensor naming/shape convention -- are ingested through both crates and must produce byte-for-byte identical generated token ids for identical input token ids (driven via `PromptInput::TokenIds` specifically to isolate weight/architecture correctness from the two bundles' deliberately different tokenizer implementations). Any transpose, shape-reversal, or naming bug would almost certainly change the result. (2) A real, downloaded, digest-pinned `Qwen2.5-0.5B-Instruct-GGUF` checkpoint (`qwen2.5-0.5b-instruct-fp16.gguf`, an unquantized F16 export, matching this ingestor's real scope) produces the exact same output (`" 1000000"` for the prompt `"The capital of France is"`, greedy) as `loaders/huggingface`'s already-verified output against the equivalent real Safetensors checkpoint for the same prompt -- independent confirmation on real model weights, not only a synthetic fixture.

## Risks / Trade-offs

- **`weight_layout.rs`/`derived_lm_head.rs` are ported, not shared, between `loaders/huggingface` and `loaders/gguf`.** A future correctness fix to one must be manually mirrored to the other. Accepted because the two crates are independent externalized modules by design (`production-model-ingestion`'s externalization boundary) and cannot depend on each other; a shared internal helper crate would need its own externalization story for marginal benefit given how small (under 150 lines each) and stable (unchanged since `implement-production-qwen-model-loading`) this logic already is.
- **GGUF quantization support is a real, visible gap, not silently deferred.** A caller with a quantized-only GGUF checkpoint gets a clear, structured `UnsupportedFormat` error naming the unsupported tensor and dtype, not a confusing failure deep inside weight materialization or a wrong numeric result.
- **The real-checkpoint test is `#[ignore]`d (manual/nightly only)**, matching `tests_real_checkpoint_smoke.rs`'s own established pattern for the same reason (a ~1.2GB download unsuitable for per-PR CI). The fast synthetic cross-format parity test provides the strong, fast, per-PR correctness signal instead.
