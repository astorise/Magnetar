## Context

Every prior sub-change in this session's multi-device chantier (`add-real-second-gpu-cuda-provider`, `add-real-peer-to-peer-gpu-movement`, `add-real-per-device-memory-feasibility-ranking`, `add-real-device-loss-degraded-replan-state-machine`) proved a real, low-level, Provider-agnostic capability against real hardware -- none of them touched `ModelInstance`/production Qwen generation at all, by design (`tests_multi_device_cpu_cuda.rs`'s own module doc explicitly bypassed the full graph/`ModelInstance` pipeline, since `ModelInstancePlacement` structurally binds one Provider/Device per instance). This change is the one that finally reaches that pipeline.

Initial investigation of a naive approach found `ctx.provider: Arc<dyn ProviderExecutionApi>` (the field every per-node dispatch call in `first_native_runtime.rs` reads) is a single fixed field on `QwenDispatchContext`, read at 30+ call sites across a 14,865-line file. Making per-node execution genuinely Provider-varying (not just Kernel-selection-varying, which already works) would mean touching most of them. Given a real production Qwen Component (`components/qwen`) also had zero support for partial/layer-range graph building at all, the user chose the safe path over two rounds of `AskUserQuestion`: reuse existing, already-verified single-Provider machinery unchanged, via two separate ordinary `ModelInstance`s and explicit movement between them, phased and verified at every step.

## Goals / Non-Goals

**Goals:**
- Real per-Device pipeline placement for a production Qwen `ModelInstance`'s decoder stack, built entirely from existing, unmodified single-Provider execution machinery.
- Real, hardware-verified proof at every phase boundary before building the next phase on top of it: synthetic-fixture bit-exact correctness (B.1) before real 2-GPU hardware (B.2) before a real, public, large checkpoint with real multi-step decode (C).
- Zero changes to `ModelInstancePlacement`'s own structure, `ctx.provider`'s single-field shape, or any existing single-Provider call path's behavior.

**Non-Goals:**
- Restructuring `ModelInstancePlacement` to span multiple Devices within one Instance -- deliberately punted per the chosen "safe" design.
- Replacing the explicit Host round trip between segments with the real, already-proven zero-Host-round-trip `CudaExecutor::copy_tensor_from_peer_admitted` primitive for this specific boundary tensor -- a real, well-scoped follow-up, not required for this change's own correctness (the boundary tensor's real numeric values are identical either way, proven bit-for-bit by Phase B.1).
- A general N-way (more than two) segment split, or an automatic layer-range-to-Device assignment policy -- every phase here uses a caller-chosen, even two-way split.
- Wiring `MultiDevicePlacementPlan` to actually gate or drive this dispatch -- it remains, as `multi-device-placement`'s own spec already states, a descriptive record nothing in this codebase consults to decide anything.

## Decisions

- **Two separate `ModelInstance`s + explicit movement, not a `ctx.provider`-generalizing rewrite.** Reused 100% of already-verified single-Provider dispatch machinery (`execute_qwen_graph`, `prepare_first_native_plan_for_graph`, weight materialization, KV commit) unchanged; the only genuinely new logic is graph-range filtering (manifest/weights) and the boundary-tensor hand-off, both far smaller and more reviewable than touching 30+ call sites' provider resolution.
- **Phase-by-phase, verify-then-build, never skip a rung.** B.1 (synthetic, Reference CPU, bit-exact) before B.2 (real hardware, prefill only) before C (real checkpoint, real decode). Each phase's own real test run caught a real bug the previous phase's scope couldn't have: B.1 caught the KV-collection Vec-position bug and the Component's tied-embeddings alias bug; B.2 and C's real-hardware dispatches confirmed the segment machinery genuinely works on real Devices; C's own real diagnostic round-trip (see below) caught a bug in the new integration test's own sampling code, not in production code.
- **`QwenLayerKvMap` (`BTreeMap<usize, FirstNativeLayerKvState>`), not a `Vec`, for per-layer KV state.** A `Vec`'s position only equals a real layer number when every layer 0..N is touched -- true for every graph before segment graphs existed, false for a segment touching an arbitrary `[start, end)` range. Every real consumer (`kv_history` lookup, the KV commit/promotion path publishing each layer's K/V under its own real layer number) was rewritten to use the explicit key instead of trusting positional alignment, catching this before it could ever produce silently wrong data for a real segment decode step.
- **Diagnosed the real Phase C hardware failure with temporary, reverted instrumentation rather than guessing.** The real two-GPU checkpoint test failed with a CUDA embedding-kernel bounds error. Rather than iterating blindly, added temporary `eprintln!` diagnostics to `providers/cuda`'s embedding dispatch (real resource ids, shapes, then real id values) and dispatched two real GPU CI rounds. The first round confirmed table/ids shapes and resource ids were always correct at every real dispatch, ruling out the entire segment weight-loading/graph-building/KV-threading surface this change built. The second, printing real values, caught the exact out-of-range id (607964, against a real 151,936-token vocabulary) and traced it to the *test's own* greedy-sampling step: `argmax` over prefill's entire flattened `[sequence_length, vocab_size]` logits tensor instead of just its last row. Fixed in the test; the CUDA instrumentation was reverted once its diagnostic job was done, leaving `providers/cuda` byte-identical to before this investigation.

## Risks / Trade-offs

- **The Host round trip between segments is real but not the fastest possible path.** `CudaExecutor::copy_tensor_from_peer_admitted` already proves zero-Host-round-trip movement is possible; not using it here for this specific boundary is a real, deliberate performance trade-off (simplicity and reuse of proven machinery), not a correctness gap -- documented in both `run_first_native_graph_segment_dispatch`'s own doc comment and this design.
- **Real Phase C verification used a small, bounded generation (6 tokens: 1 prefill + 5 decode) rather than a long generation.** Chosen to keep real GPU CI wall time reasonable (this test's own real cost is roughly double a single-GPU run's, per step, across two real Providers); the real multi-step KV-threading logic exercised is the same regardless of length -- a longer run would exercise more steps of already-proven logic, not new code paths.
