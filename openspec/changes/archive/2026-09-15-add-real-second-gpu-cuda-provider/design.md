## Context

`add-multi-device-cpu-cuda-execution-proof`'s own design.md listed "peer-to-peer GPU-to-GPU movement or per-Device memory feasibility ranking against a real multi-GPU budget" as a Non-Goal specifically because "no second GPU exists here to exercise either against". The user directly corrected that premise for the CI environment. Investigation (via the `mcp__homelab__wsl_get_host_capabilities` tool, which reported a different single GPU on this development workstation, and then real `kubectl` access to the Talos cluster via its own `kubeconfig`) confirmed the real, physical fact: `arc-gpu-magnetar`'s host node has `nvidia.com/gpu: 2` capacity and allocatable, while its own job-pod resource request capped every job at 1. Three sibling job-hook ConfigMaps on the same cluster (`arc-candle-*`) already requested 2, making this a real, isolated configuration gap rather than a hardware limitation.

## Goals / Non-Goals

**Goals:**
- A real, hardware-verified two-GPU execution proof, genuinely exercising two physically distinct real GPUs (not simulated, not a single GPU asked twice).
- `CudaProvider` support for binding to a specific device ordinal, with `new()`'s existing behavior provably unchanged.
- The real infrastructure fix (raising the CI node's per-job GPU resource request) applied and verified against the live cluster, not just described.

**Non-Goals:**
- Real peer-to-peer GPU-to-GPU memory access (CUDA peer access APIs) -- both GPUs move data via an explicit host round trip, matching the CPU+CUDA proof's own pattern; peer access remains unimplemented anywhere in this repository.
- Per-Device memory feasibility ranking against a genuinely heterogeneous multi-GPU budget -- the two real GPUs available are identical RTX 3060s with identical budgets; a heterogeneous case (e.g. a 24GB + an 8GB GPU) remains unverified.
- Wiring any of this into `ModelInstance`/production Qwen graph execution -- `ModelInstancePlacement` still structurally binds one Provider/Device per instance; unchanged here.
- More than two GPUs, or dynamic GPU-count discovery beyond ordinals 0/1 specifically -- the real hardware available has exactly two.

## Decisions

- **`for_device(ordinal, provider_name)` takes an explicit Provider name, not an auto-derived one.** An auto-derived name (e.g. always `format!("{CUDA_PROVIDER_NAME}:{ordinal}")`) was considered and rejected: it would silently couple every future caller to one specific naming scheme baked into this crate, when the real reason a distinct name is needed at all is purely `ProviderLoader`'s own uniqueness constraint -- the caller, not this crate, is in the best position to decide what naming convention fits its own `Runtime`'s other registered Providers. `new()` picks `CUDA_PROVIDER_NAME` for backward compatibility; the test suite and the new two-GPU integration test both use `"magnetar:provider/cuda:1"` as a real, readable convention, but that is a caller choice, not an enforced one.
- **Thread `provider_name` as a plain `&str`/`impl Into<String>` parameter through the existing single-device functions, rather than restructuring `CudaProvider` to hold multiple devices internally.** A "one Provider, many Devices" shape (mirroring how ROCm/ Level Zero conceptually work) was considered, since it would avoid the `ProviderLoader` naming problem entirely. Rejected for this change: it would require `CudaExecutor`/`CudaKernels`/the device-resident allocation table to become dtype- and device-polymorphic (one `CudaContext` per device, kernels compiled per-context), a substantially larger, riskier rewrite than the two-real-GPU proof this change specifically needed. The "one Provider per real GPU ordinal, distinctly named" shape reuses every existing single-device code path unchanged, verified by `for_device_zero_matches_new_exactly`.
- **Fix the real infrastructure gap directly, not just document it.** The `nvidia.com/gpu: 1` limit was a genuine, isolated misconfiguration (sibling job hooks on the same cluster already used 2) rather than an intentional constraint -- confirmed via `kubectl describe node`'s real capacity report before touching anything. Applied via `kubectl apply` against the live cluster's own `kubeconfig`, then re-verified with a real `gpu-runner-smoke.yml` dispatch showing both GPUs in `nvidia-smi`'s own output, before any of this change's Rust code was written -- the same "verify for real, not by assumption" discipline this repository's entire development history follows.
- **A dedicated `stage_from_provider` helper, not duplicated Stage-construction boilerplate.** The existing CPU+CUDA test built each `Stage` by hand inline; adding a second, near-identical block for GPU0/GPU1 would have tripled that boilerplate. Extracted once, used by the new test; the existing CPU+CUDA test was left untouched (already verified, not worth the risk of an unrelated regression to satisfy pure DRY).

## Risks / Trade-offs

- **The infrastructure fix lives outside this repository's own git history** (`talos/arc-magnetar-gpu-job-hook.yaml`, applied via `kubectl apply`, not tracked by any change this repository's OpenSpec process versions). A future reader of this repository alone cannot see why the CI node started reporting two GPUs; this design.md and the integration test's own doc comments are the only record inside this repository.
- **A real bug this change's own verification found and fixed along the way**: `for_device_one_reports_against_the_real_device_count`'s first version called `cudarc::driver::CudaContext::device_count()` directly, which panics (not `Err`) when the CUDA shared library is completely absent -- crashing outright on CI's genuinely CUDA-library-less `provider-integration`/`submodule-integration` runners instead of gracefully reporting "no driver". Fixed by wrapping the call in the same `std::panic::catch_unwind` guard `CudaProvider::new()`/`for_device` already use internally for the identical real `cudarc` behavior.
- **Both real GPUs happen to be identical hardware** (RTX 3060 x2) -- this proof does not exercise the "heterogeneous Devices" requirement `multi-device-placement`'s own spec already states as a goal; that remains real, unverified future work pending access to genuinely different GPU models.
