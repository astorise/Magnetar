## Context

Two pieces already exist and are unaffected by this Change: `formats/safetensors::parse` (real, tested, produces `SafetensorsArtifact { tensors: Vec<ModelTensorMetadata>, metadata }`, deliberately not copying tensor data itself -- see its own design.md), and `magnetar-runtime`'s `materialize_model_instance_weights` (real, tested, generic, takes `&BTreeMap<String, HostTensor>`). The gap between them is narrow and mechanical: something must read the actual tensor bytes out of a real file using the offsets `SafetensorsArtifact` already validated, and hand the result to the existing materialization function. `externalize-runtime-extension-modules`'s new normative requirement constrains where that "something" can live: `magnetar-runtime` itself SHALL have zero *compile-time* dependency on `formats/safetensors`.

**Correction made while implementing, not anticipated when this design.md was first written:** that constraint is stricter than it first appears, and empirically re-verified rather than assumed -- `formats/safetensors` was temporarily added as a `magnetar-runtime` `[dev-dependencies]` entry, the CI guard's two checks (`externalize-runtime-extension-modules`'s own addition) were run against it, and then it was reverted. Result: the manifest-text check (a plain grep of `magnetar-runtime/Cargo.toml`) catches it -- it does not distinguish `[dependencies]` from `[dev-dependencies]`, so any section naming the crate trips it. (`cargo tree --all-features`, the guard's *second* check, does not include dev-dependencies by default and would have missed it alone -- the manifest check is what actually closes this path, not the tree check, a detail worth recording precisely rather than hand-waved.) So `formats/safetensors` cannot be a `magnetar-runtime` dev-dependency either, not just not a normal one; even a test-only round-trip check calling `formats/safetensors::parse` from inside `magnetar-runtime`'s own test suite would trip the guard `magnetar-runtime` itself just added. The original draft of this section said such test-only use "is fine" -- it is not.

## Goals / Non-Goals

**Goals:**
- Close `reach-architecture-freeze-1` tasks 8.1/8.2/8.6 for real: a real byte-level Model Artifact exists, gets parsed through the real parser, and materializes through the existing generic phase.
- Preserve the dependency-direction requirement `externalize-runtime-extension-modules` just formalized: no format-crate dependency enters `magnetar-runtime`'s production code.
- Prove correctness, not just presence: a parity test against the existing in-memory path's known-good output.

**Non-Goals:**
- Arbitrary real-world checkpoint loading via `magnetar-cli` (needs tokenizer.json/config.json support, real separate roadmap work).
- Non-f32 storage dtype support in the new bridge function. `HostTensor` itself is f32-only by design (`reference_cpu.rs`'s own module doc); the fixture's weights are f32; a real checkpoint using F16/BF16 storage would need a dtype-conversion step this Change does not add. The bridge function rejects non-f32 tensors with a structured error rather than silently reinterpreting bytes.
- GGUF fixture parity. The mechanism this Change proves generalizes to GGUF trivially (same bridge function, any format's `Vec<ModelTensorMetadata>`), but duplicating the fixture work for both formats is not needed to prove the mechanism once.
- Changing `ModelLoadingCoordinator::load()`'s signature or the Lazy Loading Policy -- already decided against by `model-loading-materializes-weight-resources`.

## Decisions

**The bytes-to-`HostTensor` bridge lives in `magnetar-runtime`, is fully generic, and never imports a format crate.** Its final signature is `fn host_tensors_from_artifact_bytes(tensors: &[ModelTensorMetadata], bytes: &[u8], data_section_start: u64) -> Result<BTreeMap<String, HostTensor>, ModelLoadingError>`: for each tensor, reads `offset_bytes`/`size_bytes` from `bytes` starting at `data_section_start + offset_bytes` (see the next decision for why that third parameter exists and was not part of the original design), verifies `storage_dtype == ModelDType::F32` (rejecting anything else structurally), reinterprets the byte range as a `Vec<f32>` (checked length: `size_bytes` must equal `shape`'s element count times 4, mirroring the same discipline `formats/safetensors` itself already applies), and constructs a `HostTensor`. This function's only inputs are types `magnetar-runtime` already owns (`ModelTensorMetadata`, `ModelDType`, `HostTensor`) plus a raw byte slice and an offset -- it has no way to depend on `formats/safetensors` even by accident, satisfying the externalization requirement structurally, not just by convention.

**Real bug found and fixed while implementing this Change's own parity test, not designed in from the start: `offset_bytes` is relative to the tensor-data section's start, not the whole file.** The first version of `host_tensors_from_artifact_bytes` treated `tensor.offset_bytes` as an absolute offset into `bytes`. It compiled, every shape/size check passed, and the function returned successfully -- but `e2e_fixture_real_artifact_weights_match_in_memory_weights` (this Change's own parity test, run *before* wiring the production cutover, per the next decision) failed with denormal and absurdly large float values for every tensor after the first. Root cause: `formats/safetensors::parse` (and `formats/gguf::parse`) both construct `ModelTensorMetadata.offset_bytes` directly from the file format's own `data_offsets`/`offset` field, which every real Safetensors/GGUF file defines relative to where the tensor-data section begins (`8 + header_length` for Safetensors; a computed alignment boundary for GGUF) -- not relative to byte zero of the whole file. Reading at the wrong absolute position was, for most tensors, reading into the middle of the JSON header or a neighboring tensor's bytes, reinterpreted as `f32`. Fixed by adding the `data_section_start` parameter above; the caller (which already parsed the header to get `Vec<ModelTensorMetadata>` in the first place) is the one who knows this value, so the generic bridge does not need to guess or hardcode it. This is exactly the kind of gap the parity-before-cutover discipline (see below) exists to catch -- and did.

*Alternative considered:* have `formats/safetensors` itself expose a "give me materialized `HostTensor`s directly" convenience function. Rejected -- `HostTensor` is a `magnetar-runtime` type; a format crate constructing it would invert the dependency direction the whole module-boundary architecture (`providers/cpu`, `components/qwen`, both format crates) has consistently kept in one direction. The bridge belongs on the `magnetar-runtime` side of the boundary, not the format-crate side.

**Fixture file generation: the writer lives in `formats/safetensors`, reversing this section's original decision.** The original draft of this design.md put a minimal writer in `magnetar-runtime`'s own test code instead, reasoning that `formats/safetensors` shouldn't grow writer scope for one fixture's sake. That reasoning did not account for the dependency-direction consequence worked out above: proving the checked-in fixture file is genuinely parseable by the real parser (round-tripping it) requires calling `formats/safetensors::parse` from *somewhere*, and `magnetar-runtime` -- production *or* test code -- cannot be that somewhere. `formats/safetensors` already legitimately depends on `magnetar-runtime` (the established, one-directional pattern every module follows), so it is the only crate that can naturally call both `magnetar-runtime`'s public fixture-generation functions (`e2e_fixture_config`, `e2e_fixture_weights`, both already `pub`) *and* a Safetensors writer, in the same test. Given the writer has to live somewhere `formats/safetensors`-side regardless, adding it as a small real `serialize`/`build` function in that crate's own production code (symmetric with `parse`, encoding the same layout `parse` already validates) is simpler than inventing a second, `magnetar-runtime`-side writer that could never actually be exercised against the real parser anyway.

**Production `magnetar-runtime` never calls `parse()`, even for its own fixture -- it uses a deterministic, self-authored tensor inventory instead.** Because the checked-in fixture file's tensor names, shapes, and (therefore) byte offsets are fully determined by `qwen_expected_tensor_names`/`qwen_expected_tensor_shape` in a fixed, known generation order, `first_native_runtime.rs` can construct the exact same `Vec<ModelTensorMetadata>` a real parse would produce, in Rust, without depending on `formats/safetensors` to get there -- the same way `qwen_expected_tensor_names` already describes the fixture's own tensor set without deriving it from any file. `include_bytes!` embeds the real file's raw bytes; this self-authored inventory plus `host_tensors_from_artifact_bytes` reads the real bytes at the real offsets. What proves the format is genuinely correct and parseable -- not just internally self-consistent -- is `formats/safetensors`'s own test suite successfully parsing this exact checked-in file with the real, independent parser; `magnetar-runtime`'s production path benefiting from a real, externally-verified file without needing to depend on the crate that verified it is exactly the module-boundary architecture working as intended, not a shortcut around task 8.2's "parse/read those bytes through Model Loading" -- the bytes genuinely are parsed and read, by the real parser, just not by `magnetar-runtime`'s own runtime code for its one fixed, already-known fixture.

**The parity test compares the old and new paths before the old path is deleted -- and this is not a hypothetical discipline, it is what actually caught the `data_section_start` bug above.** A test loads the fixture both ways (existing in-memory `e2e_fixture_weights()`, and the new real-file path) within the same test, asserts the resulting `HostTensor` maps are equal, and only *then* is the old in-memory call site in the production path (`bind_qwen_fixture_weights`) actually switched over, keeping its existing digest-check gate (`e2e_fixture_weight_digest(&fixture.weights)`, unchanged) as the tamper-detection mechanism while switching what gets *materialized* to the real-artifact-sourced weights. This mirrors task group 11.5's own working pattern this session (graph-fingerprint parity caught real mismatches before the old path was retired) -- proving equivalence before cutover, not assuming it, and it earned its keep again here.

**Computing `data_section_start` for the self-authored fixture reads only the file's own 8-byte length prefix, nothing more.** `e2e_fixture_weights_from_real_artifact` (the fixture-specific caller in `first_native_runtime.rs`) reads `E2E_FIXTURE_SAFETENSORS_BYTES[..8]` as a little-endian `u64` and adds `8` -- the exact same arithmetic `formats/safetensors::parse` does internally, but without parsing any JSON, validating any tensor, or otherwise depending on that crate. This is judged to be within the line drawn elsewhere in this design.md ("production never calls `parse()`"): reading a fixed-width length prefix is not format *parsing* in the sense the externalization requirement is protecting against, and a local `HEADER_LENGTH_PREFIX_BYTES = 8` constant documents exactly why this one number is duplicated rather than imported.

## Post-acceptance correction (external audit, 2026-09-03)

**This Change's "Weight Resource Completeness Gates Generation" requirement was itself wrong when first written, and has been corrected in place, not superseded by a contradicting delta elsewhere.** Its original wording said Model Instance creation "MAY report an instance as structurally ready before" weight materialization, relying only on a deeper graph-dispatch-time check (a missing weight edge failing to resolve) to fail closed. An external audit of PR #36 (commit `0197be1`) correctly identified this as an incomplete guarantee: `ModelInstances::acquire_usage`'s own readiness check inspects only the instance's coarse `readiness` flag, not its weight bindings, so nothing in the type/API surface actually prevented a future caller from treating a `Ready`-but-unmaterialized instance as usable -- the deep dispatch-time check happening to also exist was a safety net, not the instance's own readiness being trustworthy. A session-internal review had already asked this exact question and concluded (with the person directing the work) that no code change was needed, checking only whether a *missing* weight fails at dispatch time (it does) without examining whether Model Instance *creation itself* should report readiness at all. That was real verification, but of the wrong property. The requirement text is now corrected to say what should have been true from the start: creation SHALL leave the instance non-Ready until materialization completes and itself transitions it to Ready. See `transactional-weight-materialization` for the implementation (transactional materialization via a `WeightMaterializationTransaction`, admission-before-Provider-write ordering, residency-error propagation, full rollback on partial failure, and Provider-owned weight storage release on unload -- none of which this Change's own scope originally covered either, since it focused on real-artifact-byte sourcing, not materialization transactionality).

## Risks / Trade-offs

- [Risk] A hand-rolled test-only Safetensors writer could itself have a bug that happens to round-trip correctly through this Change's own reader but would not match a real third-party Safetensors file's exact byte layout. → Mitigation: the writer produces exactly the format `formats/safetensors::parse`'s own unit tests already validate against (header length prefix, JSON header shape, `data_offsets`); no new encoding invented, only the existing decoding's inverse.
- [Trade-off] Scoping the bridge function to f32-only defers real dtype-conversion-on-load support. Accepted: the fixture and every real Qwen graph node this repository currently exercises are f32-only already (`Reference CPU only ever stores f32 elements`); adding dtype conversion on load is real, valuable, separate work for whenever a quantized or f16-native checkpoint is the actual target, not invented speculatively here.
