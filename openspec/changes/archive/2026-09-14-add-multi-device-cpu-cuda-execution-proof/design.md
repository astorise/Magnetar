## Context

`multi_device_placement.rs` already existed, fully real at the data-model level (24 of its own unit tests, real SHA-256 fingerprinting, a real eligibility/cost-ranking algorithm), but genuinely disconnected from execution: nothing in `execution_graph.rs`, `kernel_dispatch.rs`, or `model_instance.rs` ever constructs or consults a `MultiDevicePlacementPlan`. Research into the actual dispatch seam found that `KernelDispatchPlan` (a different, lower-level type) already carries its own `provider`/`device` binding per invocation, and nothing in `Runtime::register_provider` or `KernelRegistry::select` structurally prevents more than one Provider's Kernels from coexisting in one Registry -- the seam for a real multi-Provider proof already existed; it had simply never been exercised with two real Providers' candidates genuinely both present.

## Goals / Non-Goals

**Goals:**
- A real, hardware-verified execution spanning two real, heterogeneous Devices in one Runtime -- not a synthetic fixture and not merely two independent single-Provider runs compared afterward.
- Explicit, real cross-Device movement (a genuine host round trip, not implicit sharing) between the two stages.
- Discovering and documenting real Kernel Registry behavior under genuine multi-Provider conditions, rather than assuming the existing single-Provider-tested code generalizes correctly.
- Wiring `magnetar-runtime`'s existing `multi_device_placement` types to real execution data for the first time, without modifying that module (it needed no changes -- every constructor and field this proof needed was already public and already correct).

**Non-Goals:**
- Full `ModelInstance`-level multi-Device placement (the existing spec's own "Model spans two GPUs" scenario) -- `ModelInstancePlacement` structurally binds one Provider/Device per instance via one `ResourceAffinity` field; changing that is a separate, much larger change this repository's one-real-GPU tooling could not verify meaningfully end to end regardless.
- Peer-to-peer GPU-to-GPU movement, per-Device memory feasibility ranking against a real multi-GPU budget, Device-loss/degraded-replan behavior, or placement-generation republishing under live in-flight traffic -- none of these have a real second GPU to exercise against here.
- Having `MultiDevicePlacementPlan` actually gate or drive dispatch -- it remains, after this change, a real, structurally-validated record built from an execution's results, not yet a contract anything consults before or during dispatch.

## Decisions

- **Bypass the full first-native Qwen graph/`ModelInstance` pipeline; drive the generic Kernel dispatch contract directly.** Reusing `execute_qwen_graph` and friends would require first solving the larger `ModelInstancePlacement` single-Provider constraint this change deliberately does not attempt to solve. `providers/cuda`'s own `tests_hardware_hot_path.rs` already established the precedent for exercising `KernelSelectionRequest -> KernelRegistry::select -> KernelDispatchPlan::from_selection -> KernelDispatcher::revalidate -> submit_kernel/complete_kernel` directly, at the minimum necessary level, without the Qwen-specific machinery.
- **Select each stage's own candidate explicitly from the full candidate list, not `selection.selected`.** Found necessary by running the first version of this test: `KernelRegistry::select`'s ranking (`fallback_rank`, `pressure_score`, `estimated_cost`) is Provider-agnostic and does not treat the request's `ResourceAffinity` as an exclusion filter against a candidate's own Provider -- confirmed by reading `candidate_for_entry` (`kernel_registry.rs`), which never compares a candidate's `advertisement.id.provider` against `request.affinity`. A caller that needs a specific Provider, as real Multi-Device placement conceptually requires, must do this selection itself; this change documents that as a real, current fact about this codebase rather than papering over it with an assumption-driven assertion.
- **Set an explicit `dtype_requirements` on the selection request.** A second real finding: CUDA advertises both a plain `f32` `add` Kernel and an `add-half` (`Float16`/`BrainFloat16`) Kernel under the same `OperatorId` (`wire-cuda-half-precision-into-kernel-registry-dispatch`); an empty `dtype_requirements` left both nominally `compatible`, and `add-half` was being selected ahead of the real `f32` `add`, failing only later at `complete_kernel` with `KernelDTypeUnsupported` -- selection alone did not catch it without this.
- **Populate `MultiDevicePlacementPlan` after both stages have already executed and been asserted correct, not before.** An independent review of this change's own draft correctly flagged that framing this as the Plan "driving" execution would overstate what the code does -- nothing in this codebase consults `MultiDevicePlacementPlan` to gate or route dispatch. It is built from the run's own real Device/result data as an explicit, structured, real record, and its own state machine (`Building` -> `Validating` -> `Ready`) is exercised for real, but it does not control the execution that produced the data it now describes.

## Risks / Trade-offs

- **This proof is deliberately narrow (`add`, elementwise, no weights, no KV cache)** -- it establishes that the seam works, not that every Kernel/Operator in this repository's catalog behaves identically across a multi-Provider Registry. A future Kernel with a real dtype/memory-class collision across Providers, structured the same way `add`/`add-half` were, would need the same explicit-candidate-selection discipline this change's own `dispatch_add` helper establishes.
- **The real Kernel Registry ranking behavior this change documents (no Provider-affinity exclusion) is a genuine, load-bearing fact a future caller must know**, not an incidental detail: any future code that assumes `KernelRegistry::select`'s `.selected` respects a caller's intended Provider will be wrong under genuine multi-Provider conditions, exactly as this change's own first draft was.
