The checked-in real Qwen Component (`components/qwen`, the strict/default production graph source) is unmodified and still declares standalone `gate_proj`/`up_proj` nodes; `providers/cpu`/`providers/cuda` still do not implement `"split"` (it is not in `operator-scope`'s required-now set, added instead as `first_decoder_optional` alongside `gelu`) -- this closes the group entirely within the existing Reference-CPU-only test-oracle boundary, touching no device-specific Provider code.

## 5. Migrate the generic per-node transport

**Un-deferred and completed** per the post-freeze équipe review (`magnetar-pr36-decisions-equipe-2026-09-02.md`, decision 8: "migrate the generic transport to `TensorValue` now -- do not wait for a real CUDA Provider"). The original deferral reasoning below (kept for record) was overridden explicitly: proving the contract is Provider-agnostic in principle (group 4's tests) is not the same as the generic dispatch layer actually carrying it, and the two-pathway risk design.md itself named does not wait for a second real Provider to become real.

<details>
<summary>Original deferral reasoning (overridden by decision 8, kept for record)</summary>

Every current Kernel *computation* (`dispatch_qwen_matmul`, `rmsnorm`, `rope_per_head`, attention, ...) is Reference CPU's own Rust code operating on `HostTensor.data: Vec<f32>` directly, and stays that way regardless of this Change -- a device-resident Provider would have its *own* Kernel implementations operating on its own buffers, never routed through `dispatch_reference_cpu_operator` at all. Given that, wrapping `execute_qwen_graph_nodes`'s read/write calls in `TensorValue::Host(...)` and immediately unwrapping via `into_host` right before handing values to `dispatch_reference_cpu_operator` (which still requires raw `HostTensor` to compute) would change zero behavior today -- Reference CPU is the only real Provider, and it never produces `Opaque`.

</details>
