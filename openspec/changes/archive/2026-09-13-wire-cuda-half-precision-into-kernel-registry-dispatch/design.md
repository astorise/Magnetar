## Context

`enable-native-cuda-half-precision-elementwise-compute`'s `design.md` left an explicit open question: "does the Kernel Registry already support two same-Provider implementations of one Operator distinguished only by dtype? unconfirmed." Investigating before implementing (this session's established practice) found the answer directly: `KernelRegistry.entries` is keyed by `KernelId::stable_key()` (`"{provider}:{name}@{version}:{operator}"`), and `KernelRegistry::candidates()` matches every entry whose implemented Operator matches the request -- nothing restricts registration to one Kernel per (Provider, Operator) pair. A same-Provider pair distinguished only by `KernelId.name` and advertised dtype set was already structurally legal; it simply had no precedent within one Provider (only across Providers, e.g. Reference CPU vs. CUDA both implementing `matmul`).

Also found: `KernelSelectionRequest.dtype_requirements` is already populated (`merge_graph_edge_requirements`) directly from each resource's own declared `TensorDescriptor.dtype` -- there is no separate "compute dtype negotiation" layer to build. A caller that wants CUDA's half-precision `add` selected over its `f32` one simply declares the resource's dtype as `Float16`/`BrainFloat16` when building the `KernelSelectionRequest`; the existing `dtype_compatible` filtering in candidate matching does the rest, unmodified.

## Goals / Non-Goals

**Goals:**
- Make Phase 2's `add_half`/`mul_half` selectable and dispatchable through the *exact* generic Kernel Registry/dispatch contract every other Kernel in this codebase uses.
- Verify with a real-hardware test that exercises that exact contract (`KernelSelectionRequest` -> `KernelRegistry::select` -> `KernelDispatchPlan::from_selection` -> `KernelDispatcher::revalidate` -> `submit_kernel`/`complete_kernel`), not merely a direct `CudaKernels` method call (Phase 2's own tests already cover that).

**Non-Goals:**
- Making the device allocation table (`CudaExecutor`'s `Mutex<BTreeMap<TensorResourceId, CudaDeviceBuffer>>`) dtype-polymorphic, so a half-precision resource could stay device-resident as real half-precision bytes *between* Kernel invocations the way every `f32` resource already does. Investigated first: this table is read/written by ~6 `ProviderExecutionApi` methods (`write_tensor_admitted`, `read_tensor`, `resident_shape`, `copy_tensor_admitted`, plus `run_invocation`'s internal get/store), all currently assuming `f32`; making it dtype-polymorphic would need either a second table or an enum wrapping both buffer kinds, with a match arm added to every one of those methods -- a real, bounded, but separate increment, deferred rather than bundled into this change's narrower scope.
- Any Model Component or production graph (Qwen included) requesting `Float16`/`BrainFloat16` compute for any real generation step. This capability remains reachable only by a caller that explicitly constructs a `Float16`/`BrainFloat16` request -- proven here by a dedicated test, not by wiring it into any actual inference path.
- `matmul`/`rmsnorm`/`rope`/`attention` gaining a half-precision-dispatchable variant. Still `add`/`mul` only, per Phase 2's own scoping.

## Decisions

- **A resource requesting `add-half`/`mul-half` round-trips through the host inside `run_invocation`'s new dispatch arm** (download the `f32`-stored inputs, `upload_half`, compute, `download_half`, re-`upload` the `f32` result) rather than requiring the storage table to already hold half-precision bytes. This is the direct consequence of the Non-Goal above: it makes the *compute* real (genuine on-device half-precision arithmetic, genuine rounding, bit-exact-verified against the reference conversion model) without requiring the *storage* retrofit. The cost -- extra host round trips per half-precision invocation, unlike this crate's usual device-resident chaining -- is accepted and documented as a real, known limitation of this narrower scope, not hidden.
- **`add-half`/`mul-half` advertise both `Float16` and `BrainFloat16` on one `KernelId`** (matching how `CudaHalfBuffer`/`add_half`/`mul_half` already handle either at runtime via `CudaHalfDType`), with the actual dispatched format recovered from the invocation's own input `TensorDescriptor.dtype` (`half_dtype_from_descriptor`) -- not a separate advertisement per format. Consistent with how the existing `f32`-only advertisements already declare exactly one dtype per role without per-value branching needed elsewhere.
- **No change to `magnetar-runtime`.** The investigation found the missing piece was Provider-side (advertisement + dispatch), not Runtime-side (selection/dtype-matching already works generically); this change touches only `providers/cuda`.

## Risks / Trade-offs

- **A half-precision resource is not actually device-resident between calls in this change** -- a second, later change would be needed to realize that, and until then this capability's real-world value is limited to "one `add`/`mul` step in isolation," not a chain of half-precision operations that stays on-device throughout. Accepted, matching the established incremental pattern (Phase 2 landed compute before residency; this phase landed dispatch before residency too).
- **Still entirely unreachable from any production graph.** Proven real and dispatchable through the standard contract, but nothing in the Qwen generation path (or any other) requests it. A future change would need to decide, deliberately, where and whether real generation should ever request half-precision compute for `add`/`mul` -- a product/correctness decision this change does not make.
