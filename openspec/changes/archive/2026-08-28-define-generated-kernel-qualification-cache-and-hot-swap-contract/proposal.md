# Define Generated Kernel Qualification Cache And Hot Swap Contract

## Why

Magnetar now defines:

```text
KernelSourceArtifact
CompiledKernelArtifact
PreparedKernel
Provider Kernel Compilation Capability
```

This is enough to ingest and compile generated kernel implementations.

It is not enough to safely use them.

A generated kernel may:

- compile successfully but implement the wrong semantics
- work on common shapes and fail on edge cases
- silently produce NaN or Inf
- violate aliasing rules
- assume unsupported alignment
- behave nondeterministically
- access resources outside its declared contract
- regress performance
- be valid only for one hardware/compiler/driver combination
- become invalid after a Provider or driver upgrade

Magnetar therefore requires a qualification layer between compilation and
production eligibility.

The Reference CPU Provider already exists as a correctness-first baseline.
Generated kernel systems make that baseline even more important: it becomes a
portable numerical oracle against which generated implementations can be
evaluated.

## What Changes

This change defines:

- generated kernel qualification
- differential correctness validation
- qualification matrices
- trust/integrity separation
- performance benchmarking and ranking
- Qualified Kernel Artifact metadata
- content-addressed Kernel Artifact cache
- compatibility-aware cache reuse
- candidate promotion
- atomic Kernel Registry replacement
- prepared-kernel generations
- safe retirement
- rollback
- revocation
- failure containment
- observability
- conformance

## Core Principle

Compilation is not qualification.

```text
compiled != correct
compiled != trusted
compiled != qualified
compiled != active
```

A generated kernel SHALL NOT become production eligible merely because:

- compilation succeeded
- it came from an AI generator
- it is cached
- it was generated by a trusted compiler
- its source format is recognized
- it is faster in one benchmark
- it has a known Provider
- it came from a local source

The exact internal implementation MAY combine individual checks, but their

## Qualified Kernel Artifact

A Qualified Kernel Artifact represents a Compiled Kernel Artifact for which
Magnetar has recorded qualification evidence.

It SHALL NOT necessarily duplicate compiled binary bytes.

It MAY be represented as:

```text
CompiledKernelArtifact
    +
QualificationRecord
```

The qualification record SHALL be immutable for the identified artifact and
qualification profile.

## Qualification Identity

Qualification identity SHALL include enough context to prevent qualification
evidence from being reused incorrectly.

A conceptual qualification key MAY include:

```text
compiled artifact digest
Operator semantic version
qualification suite version
Reference implementation version
target architecture
Provider version
compiler/toolchain fingerprint
dtype
layout
shape profile
precision profile
determinism profile
driver/runtime compatibility
```

A qualification result for one incompatible context SHALL NOT automatically
qualify another.

## Qualification Status

Suggested states are:

```text
unqualified
qualifying
qualified
qualified-with-limitations
rejected
revoked
expired
```

`qualified-with-limitations` MAY be used when eligibility is restricted to a
precisely declared compatibility envelope.

Example:

```text
qualified:
    dtype = fp16
    shape = [batch 1..8, seq <= 4096]
    head_dim = 128
    architecture = sm90
```

Outside that envelope, Kernel Registry SHALL treat the Kernel as incompatible.

## Qualification Profiles

Qualification SHOULD use explicit profiles.

Example profiles MAY include:

```text
baseline-correctness
strict-correctness
deterministic
approximate-math
quantized
attention
fused
browser
mobile
provider-specific
production
```

Profiles SHALL be versioned.

A Kernel qualified against one profile SHALL NOT silently be treated as
qualified against a stricter profile.

## Correctness Oracle

Reference CPU Provider SHOULD serve as the default correctness oracle for
portable Operators supported by the baseline.

The oracle SHALL prioritize semantic correctness over performance.

Generated Providers/Kernels SHALL NOT redefine portable Operator semantics.

Alternative or additional reference implementations MAY be used where:

- Reference CPU does not support the required Operator
- numerical method requires specialized reference semantics
- quantized or approximate math requires a specific tolerance profile

The chosen oracle SHALL be recorded in qualification metadata.

## Differential Testing

Qualification SHOULD compare generated Kernel output against a reference
implementation.

Differential comparison SHALL consider:

- output shape
- output dtype
- numerical values
- NaN/Inf behavior
- determinism requirements
- aliasing behavior
- mutation behavior
- error behavior
- edge-condition semantics

Exact equality SHALL be required where semantics demand exact behavior.

Numerical tolerance MAY be used where Operator semantics permit it.

## Tolerance Profiles

Numerical tolerance SHALL be explicit.

Tolerance metadata SHOULD include as applicable:

```text
absolute tolerance
relative tolerance
ULP tolerance
dtype
accumulation dtype
quantization tolerance
deterministic tolerance
approximate-math allowance
```

A performance optimization SHALL NOT silently widen tolerance.

## Qualification Input Matrix

Qualification SHOULD cover a representative matrix rather than one happy-path
input.

The matrix MAY include:

- minimum supported shapes
- maximum supported shapes
- irregular dimensions
- alignment boundaries
- batch boundaries
- sequence boundaries
- head dimension variants
- empty or near-empty ranges where legal
- zero values
- negative values
- denormal values
- NaN/Inf where semantics define behavior
- masks
- extreme logits
- quantization boundaries
- aliasing cases
- in-place cases
- non-contiguous layouts where declared
- cancellation checkpoints

The matrix SHALL be derived from declared Kernel constraints.

## Shape Qualification

A shape-specialized Kernel SHALL be qualified only for the shape envelope that
was tested or otherwise proven.

Example:

```text
Kernel supports:
batch = 1..32
seq   = 1..8192

Qualification evidence:
batch = 1..8
seq   = 1..4096
```

Runtime SHALL NOT infer qualification for the entire advertised envelope unless
policy explicitly allows evidence extrapolation.

Default policy SHOULD be conservative.

## Property-Based Qualification

Qualification MAY use generated/property-based test inputs.

Property generation SHOULD remain bounded by Kernel-advertised constraints.

Property-based qualification SHALL produce reproducible seeds or equivalent
evidence where feasible.

## Metamorphic Qualification

Qualification MAY use metamorphic relations where direct reference evaluation
is expensive.

Examples MAY include:

```text
identity transformations
permutation invariants
scaling relations
decomposition equivalence
fused-vs-unfused equivalence
```

Metamorphic tests SHALL supplement, not silently replace, required reference
comparison where a correctness oracle exists.

## Fused Kernel Qualification

A fused Kernel SHALL be validated against the semantics of the Operator group
it replaces.

Example:

```text
RMSNorm
   ->
MatMul
```

may be compared against:

```text
reference_rmsnorm
    ->
reference_matmul
```

The fused implementation SHALL NOT introduce hidden semantic changes.

## Quantized Kernel Qualification

Quantized kernels SHALL use explicit quantization and tolerance profiles.

Qualification SHALL validate as applicable:

- scale interpretation
- zero points
- group size
- packing
- storage dtype
- compute dtype
- accumulation dtype
- dequantization behavior
- expected error tolerance

## Determinism Qualification

If Kernel advertises deterministic behavior, qualification SHALL test that
claim according to policy.

The test SHOULD include repeated execution with identical inputs under a
compatible execution context.

If deterministic behavior depends on execution mode, device, atomic use, or
parallel reduction, that dependency SHALL remain explicit.

## Memory Safety And Contract Qualification

Qualification SHALL verify Provider-visible Kernel contract behavior where
possible.

It SHOULD check:

- declared input/output counts
- shapes
- byte sizes
- alignment
- workspace bounds
- aliasing
- in-place rules
- mutation behavior
- resource affinity
- memory classes
- output readiness
- no unexpected resource ownership transfer

Qualification SHALL NOT grant arbitrary memory access to generated kernels.

## Failure Behavior

Generated Kernel failure behavior SHOULD be validated.

A Kernel SHALL NOT qualify if unsupported or invalid inputs produce:

- process crashes
- Provider ABI unwind
- unstructured corruption
- silent output truncation
- silent shape reinterpretation
- undefined Runtime resource state

when the declared contract requires structured failure.

## Security Qualification

Qualification SHALL be separate from trust but MAY include security checks.

Security qualification MAY include:

- source/artifact trust requirement
- compiler isolation status
- binary validation
- executable format validation
- resource-limit compliance
- banned imports/features
- sandbox policy compatibility
- static inspection
- Provider-specific safety validation

Security qualification SHALL NOT convert unauthenticated provenance into trust.

## Qualification And Trust

Qualification and trust SHALL remain separate dimensions.

A Kernel MAY be:

```text
trusted but unqualified
qualified but untrusted
trusted and qualified
neither trusted nor qualified
```

Production policy MAY require both:

```text
trusted && qualified
```

before promotion.

## Benchmarking

Performance evaluation SHALL occur only after correctness requirements required
by policy have passed.

A faster incorrect Kernel SHALL never outrank a correct Kernel.

Benchmarking MAY measure:

```text
latency
throughput
launch overhead
memory bandwidth
workspace usage
energy
compile cost
prepare cost
tail latency
```

## Benchmark Profiles

Benchmark profiles SHALL identify workload shape and environment.

A benchmark result without workload/context metadata SHALL NOT be used as
authoritative ranking evidence.

Metadata SHOULD include:

- target Device
- hardware architecture
- Provider version
- driver/runtime version
- input shapes
- dtype/layout
- batch size
- sequence length
- warmup count
- measurement count
- synchronization policy
- benchmark version

## Performance Ranking

Kernel Registry MAY use performance evidence as one ranking input.

Correctness, trust, compatibility, readiness, Resource Affinity, and policy
SHALL be evaluated before performance ranking.

Conceptually:

```text
eligible =
    semantics compatible
    && qualification accepted
    && trust policy accepted
    && Provider ready
    && Device compatible
    && memory feasible

rank eligible candidates by policy/performance
```

## Benchmark Stability

A benchmark result SHOULD NOT be considered permanently valid.

Performance evidence MAY become stale because of:

- driver changes
- Provider changes
- compiler changes
- hardware revisions
- firmware changes
- thermal/power policy
- Runtime changes

Benchmark metadata SHOULD include freshness or compatibility information.

## Regression Policy

A newly generated Kernel MAY be rejected even when correct if it violates
performance policy.

Possible policies include:

```text
must beat current active Kernel
must be within X% of active Kernel
correctness-only acceptance
memory-optimized acceptance
energy-optimized acceptance
```

Policy SHALL be explicit.

## Qualified Kernel Cache

Magnetar SHOULD support a content-addressed Kernel Artifact cache.

The cache SHALL remain distinct from:

- Model Artifact cache
- Prefix Cache
- KV Cache
- Runtime Memory Manager residency

## Kernel Cache Contents

The Kernel cache MAY contain:

- Kernel Source Artifacts
- Compiled Kernel Artifacts
- qualification records
- benchmark records
- compatibility metadata
- provenance metadata
- trust/integrity metadata

PreparedKernel native state SHALL NOT be persisted as portable cache content.

## Cache Identity

Cache identity SHOULD be content-addressed.

Compiled artifact cache keys SHOULD include enough compatibility context to
prevent unsafe reuse.

A conceptual key may include:

```text
source digest
compiled artifact digest
source format
compiled format
compiler identity/version
compiler flags fingerprint
Provider version
target architecture
driver/runtime compatibility class
Operator semantics
dtype
layout
shape specialization
device features
```

## Qualification Cache Identity

Qualification records SHALL include:

```text
artifact digest
qualification suite version
oracle identity/version
qualification profile
target context
test matrix fingerprint
tolerance profile
```

Changing any qualification-relevant dimension SHALL invalidate or separate the
record according to policy.

## Cache Hit Does Not Imply Eligibility

```text
cache hit != trusted
cache hit != qualified
cache hit != compatible
cache hit != active
```

Current Runtime policy SHALL re-evaluate metadata needed for current execution.

## Immutable Cache Entries

Content-addressed cache entries SHOULD be immutable.

Mutation SHOULD create a new digest-addressed entry rather than alter an
existing artifact in place.

Metadata that is operational rather than content identity MAY be stored
separately.

## Cache States

Suggested cache states include:

```text
partial
validating
ready
untrusted
unqualified
qualified
rejected
revoked
corrupt
retiring
evicting
evicted
```

These states describe cache management and SHALL NOT replace current Runtime
eligibility decisions.

## Cache Integrity

Cache reads SHALL validate integrity according to policy.

Corrupt entries SHALL NOT be used.

Corruption of one cache entry SHALL NOT invalidate unrelated entries.

## Cache Eviction

Cache eviction SHALL not destroy a Prepared Kernel that is still active merely
because its source/compiled artifact is evicted.

Prepared Kernel lifetime and persistent artifact cache lifetime are distinct.

Runtime MAY prevent eviction of artifacts required to reconstruct active
prepared state according to policy.

## Cache Pinning

Artifacts MAY be pinned for:

- active Model Instances
- production-approved Kernels
- offline deployment
- reproducibility
- rollback

Pinning policy SHALL be explicit.

## Cache Offline Behavior

A valid cached Compiled Kernel Artifact MAY enable offline operation.

Runtime SHALL NOT require recompilation when a compatible cached artifact is
available and policy allows reuse.

## Candidate State

A Qualified Kernel MAY become a Registry candidate without immediately becoming
active.

Suggested logical states:

```text
qualified
candidate
canary
active
retiring
retired
revoked
```

`canary` MAY be optional.

## Kernel Promotion

Promotion SHALL be explicit.

Promotion means a candidate becomes eligible/preferred for new dispatches under
a defined policy.

Promotion SHALL NOT mutate in-flight invocations.

## Atomic Registry Promotion

Kernel Registry SHOULD support atomic logical promotion.

New dispatches SHALL observe either the old selected generation or the new
generation according to a well-defined publication point.

They SHALL NOT observe partially updated Registry state.

## Prepared Kernel Generations

A logical Kernel MAY have multiple Prepared Kernel generations.

Example:

```text
KernelId = attention-sm90-generated

generation 41
    PreparedKernelId = 1201
    state = active

generation 42
    PreparedKernelId = 1278
    state = candidate
```

After promotion:

```text
generation 41 = retiring
generation 42 = active
```

## In-Flight Stability

An invocation that has acquired a Prepared Kernel generation SHALL continue to
use that generation unless execution policy explicitly supports safe migration.

Default policy SHALL NOT migrate an in-flight invocation to a different native
kernel.

## Active Reference Tracking

Runtime/Provider SHALL track enough lifetime information to prevent destroying
Prepared Kernel state while it is referenced by active work.

The mechanism MAY use:

- reference counts
- generation leases
- epochs
- in-flight counters
- Provider-specific safe-retirement mechanism

The implementation mechanism is internal.

## Safe Retirement

A retiring Prepared Kernel SHALL stop receiving new work.

It MAY be destroyed only after:

```text
active references == 0
```

or an equivalent Provider-confirmed quiescent state.

## Rollback

Runtime SHALL support rollback to a previously known-good Kernel when the
replacement is still available and compatible.

Rollback MAY occur because of:

- execution failure
- correctness alarm
- runtime error rate
- benchmark regression
- Provider fault
- operational policy
- manual operator request
- newly discovered qualification defect

## Automatic Rollback

Automatic rollback MAY be supported.

If enabled, trigger policy SHALL be explicit.

A rollback SHALL:

- stop new dispatches to the bad generation
- preserve in-flight safety
- promote a compatible known-good candidate
- record the event
- optionally mark the failing generation rejected or revoked

## Rollback Candidate

A previously active Kernel SHOULD be retained long enough to support rollback
according to policy.

Immediate destruction of the previous generation after promotion SHOULD be
avoided when rollback policy requires a rollback window.

## Revocation

Kernel Artifacts and qualification records MAY be revoked.

Revocation reasons MAY include:

- security issue
- discovered numerical bug
- corrupted provenance
- invalid compiler/toolchain
- Provider incompatibility
- broken driver combination
- qualification suite defect

A revoked Kernel SHALL NOT receive new work.

## Revocation Of Active Kernel

If an active Kernel becomes revoked, Runtime SHALL stop new dispatches to it.

Existing invocations SHALL follow policy:

```text
allow-to-complete
cancel-if-safe
fail-closed
Provider-specific
```

The policy SHALL be explicit.

## Qualification Expiration

Qualification evidence MAY expire or become incompatible after environment
change.

Examples:

```text
Provider upgrade
compiler upgrade
driver major change
qualification suite upgrade
Operator semantic version change
```

Runtime SHALL not silently treat stale qualification as current when policy
requires requalification.

## Hot Swap

Hot swap refers to replacing a logical Kernel implementation or prepared
generation without unloading the Provider.

Hot swap SHALL NOT mean unloading and reloading a Provider shared library.

Provider lifetime remains independent from Kernel lifetime.

## No Provider Hot Reload Requirement

Generated-kernel replacement SHALL NOT require:

```text
dlclose(provider.so)
dlopen(provider-v2.so)
```

Provider reload and Provider state migration remain separate future concerns.

## Model Instance Interaction

A Model Instance MAY use:

```text
dynamic Kernel selection
```

or may pin a Kernel generation set for reproducibility.

The policy SHALL be explicit.

For strict reproducibility, a Model Instance SHOULD be able to pin:

```text
KernelId
artifact digest
Prepared generation
qualification profile
```

where feasible.

## Session Interaction

Inference Sessions SHALL NOT own native Kernel state directly.

Sessions MAY inherit Model Instance Kernel selection policy.

## Continuous Batching

Kernel promotion SHALL not corrupt existing continuous batches.

A batch slot/in-flight operation SHALL retain a valid Kernel generation for the
duration required by execution semantics.

New batch work MAY use the newly promoted generation.

## Resource Affinity

Hot replacement SHALL preserve Resource Affinity constraints.

A new Kernel SHALL NOT be promoted if its prepared state is incompatible with
the required Device or tensor residency.

## Memory Manager

Persistent Kernel cache storage and Prepared Kernel executable memory SHALL
remain separate from Runtime Tensor memory.

Memory Manager MAY receive pressure information related to preparation or
executable-memory use, but SHALL retain authority over Runtime Tensor
allocation/residency.

## Qualification Service Boundary

Qualification MAY execute:

- inside Runtime tooling
- in CI
- in a dedicated local process
- in an external optimization service
- in Tachyon-managed infrastructure

Runtime inference SHALL consume qualification evidence without depending on a
specific qualification service implementation.

## Generator Independence

Qualification SHALL be generator-neutral.

The same contract SHALL apply to Kernels authored by:

```text
KernelEvolve-like systems
other AI agents
humans
vendor compilers
CI optimizers
future generators
```

## Qualification Failure Atomicity

Failed qualification SHALL NOT damage the currently active known-good Kernel.

A failing candidate SHALL remain non-active.

## Benchmark Failure Atomicity

Benchmark crashes or failures SHALL NOT remove the existing active Kernel.

## Promotion Failure Atomicity

If preparation or Registry promotion fails, the previous active generation
SHALL remain valid.

## Observability

Observability SHOULD record lifecycle events such as:

```text
qualification-started
qualification-completed
qualification-failed
differential-check-failed
kernel-qualified
kernel-rejected
kernel-revoked

kernel-retired

```

Observability MAY expose:

- KernelId
- artifact digest
- qualification profile
- target architecture
- Provider binding
- Device binding
- benchmark summary
- generation number
- failure category

Observability SHALL NOT expose by default:

- raw kernel source
- raw compiled binary
- raw test tensors
- model weights
- native handles
- executable pointers
- secrets
- credentials
- unrestricted local paths

## Conformance

Conformance SHALL validate:

- compiled does not imply qualified
- qualified does not imply trusted
- cache hit does not imply eligibility
- Reference CPU can act as oracle for baseline Operators
- differential mismatch rejects candidate
- tolerance profiles are explicit
- shape qualification is bounded
- fused semantics compare against unfused semantics
- deterministic claims are verified
- performance ranking occurs only among eligible candidates
- cache identity includes compatibility-relevant dimensions
- cache corruption fails closed
- promotion is atomic
- in-flight requests retain old Prepared Kernel safely
- retiring generation receives no new work
- destruction waits for quiescence
- rollback restores known-good generation
- revocation prevents new execution
- Provider is not unloaded during Kernel hot swap
- failed candidate cannot replace active known-good Kernel

## Non-Goals

This change does not:

- implement KernelEvolve
- embed an AI agent in Magnetar Runtime
- implement a specific benchmark harness
- prescribe one property-testing framework
- prescribe one persistent cache backend
- define distributed cache replication
- define Provider shared-library hot reload
- migrate live native invocations between Kernels
- make Reference CPU a performance baseline
- require every Kernel to outperform the current active Kernel
- define production rollout percentages
- define fleet-wide canary infrastructure

## Impact

Magnetar evolves from a Runtime that can execute generated Kernels into a
Runtime architecture capable of safely accepting, validating, ranking, caching,
promoting, replacing, revoking, and rolling back generated Kernel
implementations.

The resulting architecture becomes:

```text
Operator semantics
        |
        v
Generated Kernel Artifact
        |
        v
Compilation
        |
        v
Qualification
        |
        v
Performance ranking
        |
        v
Qualified content-addressed cache
        |
        v
Provider preparation
        |
        v
Atomic Registry promotion
        |
        v
Hot-path execution
```
