## 2. Generic materialization function

**Corrected mid-implementation: not relocated to `model_loading.rs` after all.** `model_loading.rs` deliberately has no dependency on the full `Runtime` type -- `load()` itself takes only `&mut MemoryManager` -- and `runtime.rs` already depends on `model_loading.rs` (`use crate::model_loading::{LoadedModelContext, ...}`). `materialize_model_instance_weights` needs `&mut Runtime` (Provider resolution via `resolve_kernel_execution_provider`, `ModelInstance` mutation, and the new failure-path lifecycle transition below). Moving it into `model_loading.rs` would have created a mutual file dependency for no behavioral benefit. It stays in `first_native_runtime.rs`, formally documented as implementing the new `model-loading` spec requirement instead.

- [x] 2.1 Move `materialize_model_instance_weights` from `first_native_runtime.rs` to `model_loading.rs` (signature and logic unchanged...), since it already has zero Qwen/fixture dependency -- confirm this by re-reading it once more before moving, not just trusting the prior session's note. (Re-read and confirmed zero Qwen/fixture dependency in its own logic, as the prior session's note claimed. **Not physically moved** -- see the group note above. Instead, split into a thin `materialize_model_instance_weights` wrapper and a `materialize_model_instance_weights_inner` function carrying the original logic unchanged, so the wrapper can add the failure-path lifecycle transition (task 2.3) without duplicating the per-tensor loop.)

(No change needed: `bind_qwen_fixture_weights` already called `materialize_model_instance_weights` by name, which still exists at the same location with the same signature -- only its internal structure changed.)
- [x] 2.3 At the call site that invokes materialization (`load_fixture_instance` or equivalent), set `weights_materialized` on the instance's readiness checks from the real success/failure outcome, then re-run whatever recomputes `ModelInstance.readiness` from those checks. (**Superseded by a more targeted fix, found necessary during implementation.** Tracing the actual production path found `ModelInstances::create()` marks every freshly-created instance `Ready` *unconditionally*, via a separate, simpler lifecycle-transition mechanism (`readiness_for_lifecycle`) that never consults `ModelInstanceReadinessChecks` at all -- that struct is real and used by a different consumer (`warm_model_instance`), not the Qwen/first-native instance-creation flow. Setting `weights_materialized` on a `ModelInstanceReadinessChecks` value nobody in this flow reads would not have closed the actual gap. The real fix: `materialize_model_instance_weights`'s wrapper now calls `instance.transition_to(ModelInstanceLifecycleState::Failed)` (an already-legal transition from `Ready`) on any materialization failure, before returning the error -- demoting the instance's *actual* lifecycle/readiness state directly, which `require_ready_first_native_instance`/`status().readiness.accepts_generation()` do consult.)
