## Context

`run_generation_loop_inner` (`magnetar-runtime/src/inference_api.rs`) already runs one real decode step per loop iteration, already pushes each produced token onto `generated` the instant it's sampled, and already fires an `InferenceApiObservationKind::TokenGenerated` observation at that exact point -- but only into an `InferenceApiObserver` that accumulates silently and is returned to the caller once, wrapped in the final `FirstNativeFixtureGeneration`, after every step has already run. There is no live signal a caller can act on token-by-token.

Separately, `Tokenizer::streaming_decode(state: StreamingDecodeState, token_ids: Vec<TokenId>, flush: bool) -> DecodeOutput` (a default trait method, `tokenizer.rs`) already exists specifically to decode newly generated tokens incrementally: it tracks `emitted_token_count` (so it never re-emits already-decoded text) and `pending_bytes` (so a token landing mid-UTF-8-sequence is held, not emitted as garbage, until enough bytes accumulate) across calls, and `flush: true` forces out whatever's pending at the end. This is exactly the "incremental tokenizer decode, no duplicate text, no lost partial UTF-8" primitive an OpenAI-style token stream needs -- it's just never been wired to anything live either.

`run_generation_loop_inner` itself only knows a `GenerationTokenizerReference` (an opaque reference/id), not an actual `&dyn Tokenizer` -- the real tokenizer object lives with the caller (`E2eFixture.tokenizer` in the production entry point family). So text-delta decoding cannot happen inside the generic loop; it has to happen one layer up, in the production entry point, which already holds both the real tokenizer and (after this change) the raw per-token-id events the loop now exposes.

## Goals / Non-Goals

**Goals:**
- Deliver each generated token to a caller as it is produced, not after the full generation completes.
- Reuse `streaming_decode` for the text delta so a caller never reimplements incremental, UTF-8-safe tokenizer decode.
- Let a caller stop generation cleanly from inside the per-token callback (client disconnect, backpressure) without a panic or garbled partial output.
- Zero behavior change for every existing caller of the generation loop or any existing production entry point.

**Non-Goals:**
- Async/`Stream`/channel-based delivery. The Rust mechanism is a synchronous `FnMut` callback, matching this Runtime's existing fully-synchronous call style (no caller in this codebase uses async today); an embedder wanting SSE/gRPC/WebSocket transport calls this synchronously from within its own async task and forwards each event, exactly as the proposal's "Magnetar -> token/chunk -> Tachyon -> transport -> Client" pipeline describes.
- A wire-level SSE/OpenAI-chunk format. `GenerationStreamEvent` is a Magnetar-native Rust enum; shaping it into an OpenAI `chat.completion.chunk` JSON body is Tachyon's job, matching the existing Magnetar/Tachyon boundary.
- Network-level backpressure or HTTP/SSE lifecycle (explicitly Tachyon's responsibility per the proposal). This change provides the hook a network layer's disconnect handler calls into; it does not implement a network layer.
- Continuous batching / multiple concurrent streams sharing one call. This is the same single in-flight generation shape every existing production entry point already has.

## Decisions

- **A minimal, tokenizer-agnostic per-token hook inside `run_generation_loop_inner`, additive via a new parameter.** Add `on_token: Option<&mut dyn FnMut(TokenId) -> ControlFlow<()>>` to `run_generation_loop_inner`, invoked immediately after `generated.push(step.token_id)` (same point `TokenGenerated`/`TokenCommitted` are already observed) and before the existing `if let Some(reason) = step.finish_reason { break reason; }` check. If it returns `ControlFlow::Break(())`, the loop breaks immediately with `FinishReason::Cancelled` -- reusing the exact finish reason and cleanup path cancellation already uses, not a new state. `run_generation_loop_with_execution_plans` (every existing caller) is unchanged and passes `None`; a new `run_generation_loop_with_execution_plans_streaming` passes `Some(...)`. This keeps the invasive part of the change (touching the shared loop) to the smallest possible surface: one new optional parameter, checked once, at one point, with the one behavior (early clean stop) that parameter can trigger.

- **Text-delta decoding happens in the production entry point, not the generic loop**, because that's where the real `&dyn Tokenizer` lives.

  **Revised during implementation, not as originally planned above.** The original plan called `Tokenizer::streaming_decode`/`StreamingDecodeState` per new token id, relying on its `emitted_token_count`/`pending_bytes` bookkeeping to avoid re-decoding from token 0 each step. Implementing it and running it against this change's own multi-token streaming test (a real ingested tokenizer, not the trivial byte-fallback path) surfaced that this reliance was unsound: `HuggingFaceTokenizer::decode` (`loaders/huggingface`, the tokenizer that actually backs every real production checkpoint) **ignores `streaming_state` entirely** -- it decodes exactly the token slice it is given through the real `tokenizers` crate and always returns `pending_partial_state: None`. Only `FixtureTokenizer`'s own non-delegating fallback path (a raw byte-level id-1 mapping used when no real tokenizer is wrapped) actually honors `streaming_state`. Calling `streaming_decode` with one new token id at a time against the real tokenizer therefore decoded each token in isolation, losing the underlying BPE decoder's inter-token joining (observed concretely: `"!chi!"` instead of the correct `"! c hi !"` for the same four tokens) -- a real, measured defect, not a theoretical one.

  The fix: `on_token` tracks `generated_so_far: Vec<TokenId>` (every token produced this generation, not just the newest) and `previously_emitted_text: String`. Each step, it appends the new token, re-decodes the *entire* accumulated list via the existing `decode_tokens_streaming` (the same call `finish_production_generation`'s non-streaming tail already makes on the full sequence at the end), and computes the delta as `full_text.strip_prefix(&previously_emitted_text)`. This works correctly for any `Tokenizer` implementation regardless of whether it carries genuine incremental state -- it never depends on `streaming_state` being honored at all. The cost is `O(n)` re-decode work per step (`O(n^2)` total across a generation), accepted here because correctness across the actual production tokenizer matters more than the constant-factor saving `streaming_decode` would have given if it worked; a `strip_prefix` failure (a pathological tokenizer whose earlier output could change retroactively) degrades to no delta that step rather than panicking or emitting garbage.

  This also surfaces a real, separate, pre-existing gap this change does not fix: `HuggingFaceTokenizer::decode` not honoring `streaming_state` means the `Tokenizer` Contract's own streaming-decode capability is unimplemented for the tokenizer that matters most in production. Fixing that belongs to `loaders/huggingface`, not this change (this change's own correctness does not depend on it), and is noted in this proposal's Impact/README as a known gap for a future, separate change.

- **No separate flush step is needed.** Because every step re-decodes the full accumulated sequence (not a bounded incremental buffer), the very last `Token` event already contains every byte the final non-streaming decode would -- there is no `pending_bytes` state that could be left un-flushed. The spec's "cancelled stream still flushes pending partial text" requirement is satisfied structurally: nothing is ever pending in the first place.

- **Exactly one `Finished` event, always, after the loop, whether it ended normally, hit a stop condition, or was cancelled by the callback.** `Finished { finish_reason, usage }` is built from the same `GenerationResult`/`GenerationOutput` every non-streaming entry point already returns -- not a separate, parallel accounting path that could drift from it.

- **The entry point still returns `Result<FirstNativeFixtureGeneration, InferenceApiError>`, exactly like every other production entry point**, in addition to delivering live events. A caller that only wants the final aggregate (or wants to assert `text` equals the concatenation of every delivered `text_delta`, which the test suite does) still gets it; a caller that wants only the stream can ignore the return value's `text` field. This avoids a second, differently-shaped return type existing only for the streaming path.

- **A Provider/Runtime error during a decode step still returns `Err` exactly as it does today.** The per-token callback is only ever invoked for an actually-produced token; an error terminating generation early does not synthesize a fake `Finished` event or call `on_event` with anything -- the caller's own `Err` handling (unchanged from every other entry point) is where that surfaces, consistent with "provider/runtime error propagated" needing no new mechanism.

## Risks / Trade-offs

- **A caller's `on_event` panicking would panic the generation loop.** No different from every other `FnMut` callback contract elsewhere in this codebase (e.g. `should_cancel`); not something this change introduces or needs to newly guard against.
- **`ControlFlow<()>` as the ubiquitous ergonomics for "should I stop" is a slightly unusual choice next to the existing `should_cancel: impl FnMut(&[TokenId]) -> bool` closure shape used elsewhere in the same function.** Chosen over a second bool-returning closure because `ControlFlow::Break`/`Continue` reads unambiguously at the call site (`on_event(...)?` -- no, `on_event` returns `ControlFlow` directly, not `Result`, since a "stop streaming" signal is an expected, not exceptional, outcome) whereas a bare `bool` return at a callback boundary is a well-known source of "did true mean stop or continue" bugs. `should_cancel` itself is untouched by this change.
