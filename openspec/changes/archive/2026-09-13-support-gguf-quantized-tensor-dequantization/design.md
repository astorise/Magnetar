## Context

`ModelQuantizationFormat::GgufQ4K`/`GgufQ5K`/`GgufQ8` already exist as generic `magnetar-runtime` types (added while implementing `formats/gguf`'s parser), and `formats/gguf` already recognizes these three `ggml_type` values and reports their byte size/element count -- but nothing ever read the actual quantized bytes. `host_tensors_from_artifact_bytes`/`tensor_from_raw_bytes` (Model Loading's weight materialization) already has exactly the right shape for this: it already converts `F16`/`BF16` storage to `F32` explicitly (`implement-production-qwen-model-loading` Decision 8 -- storage dtype and compute dtype stay distinct, conversion is always explicit, never inferred). Quantized formats are the same kind of problem, just with block structure instead of a flat per-element width.

## Goals / Non-Goals

**Goals:**
- Real, correct dequantization of GGUF's `Q8_0`/`Q4_K`/`Q5_K` block formats to `F32`, verified against real upstream `ggml` source, not approximated.
- Keep the exact same architectural shape F16/BF16 conversion already established: explicit, at Model Loading time, never inferred, every downstream kernel only ever sees `F32`.

**Non-Goals:**
- Wiring this into `loaders/gguf` (see the real blocker below -- a separate, well-scoped follow-up).
- GPTQ/AWQ/BitsAndBytes. Entirely different quantization schemes (group-wise integer quantization over Hugging Face/Safetensors tensors, not GGUF's block structure) needing their own separate research and design.
- Real quantized *compute* (a Provider kernel operating on quantized bytes directly, without ever materializing F32). Remains a placeholder (`reference_cpu_quantize_and_dequantize_placeholders_reject_explicitly`'s existing rejection is untouched and correctly still applies) -- a different, larger undertaking than load-time dequantization.
- Fully wiring `ModelQuantizationPolicy`'s `DirectQuantizedExecution`/`LazyDequantization`/`ProviderSpecificTransform` variants to distinct real behaviors. These remain what they already were: recorded intent with no differentiated implementation behind them (only `RejectUnsupported` is structurally enforced today, at planning time). `host_tensors_from_artifact_bytes` dequantizes unconditionally whenever it encounters a supported quantized dtype, regardless of which of the four non-`RejectUnsupported` policy variants a caller declared -- consistent with today's reality that dequantize-at-load is the only one anything can actually do, not a new inconsistency this change introduces.

## Decisions

- **Every dequantization formula and byte layout was verified directly against real upstream `ggml-org/llama.cpp` source** (`ggml-common.h`'s block struct definitions, `ggml-quants.c`'s `dequantize_row_q8_0`/`dequantize_row_q4_K`/`dequantize_row_q5_K`), fetched and cross-checked line-by-line against the actual downloaded files, not recalled from general knowledge -- this is exactly the kind of numerically-precise, easy-to-get-subtly-wrong logic where "looks plausible" and "is correct" can silently diverge.

  - `block_q8_0` (34 bytes: 2-byte `f16` scale `d` + 32 signed `int8` quants, 32 elements/block): `value[i] = d * qs[i]`.
  - `block_q4_K`/`block_q5_K` (256-element super-blocks, 8 sub-blocks of 32): both share a 12-byte packed 6-bit scale/min encoding (`get_scale_min_k4`) -- sub-blocks 0-3 read 6 bits directly from `scales[j]`/`scales[j+4]`; sub-blocks 4-7 split across a low nibble in `scales[j+4]` and the top 2 bits of `scales[j-4]`/`scales[j]`. This packing is the single most error-prone detail in a from-scratch reimplementation (confirmed by the research process itself flagging it as "the detail most naive reimplementations get wrong"), so it was verified against the real source directly and given dedicated test coverage exercising both branches, not just the simple one.
  - `Q4_K`: `value[i] = (d * scale6[sub_block]) * q4[i] - (dmin * min6[sub_block])`, `q4[i]` the raw unsigned 4-bit nibble. The 128-byte `qs` array is walked in 32-byte strides shared by *two* sub-blocks per stride (that stride's low nibbles form one sub-block, high nibbles the next) -- not two independent contiguous halves, a second easy-to-miss detail.
  - `Q5_K`: identical scale/min structure, plus a 32-byte `qh` high-bit plane (fixed across the whole super-block, never advanced per 64-element chunk, unlike `ql`) reconstructing a 5-bit value via `q5[i] = (ql[i] & 0xF) | (qh[i] & bit ? 16 : 0)`, the selected bit rotating `(1,2) -> (4,8) -> (16,32) -> (64,128)` across the four 64-element chunks.
  - All `ggml_half` scale fields are genuine IEEE-754 binary16, decoded via this codebase's existing `f16_to_f32` (already used for `F16` conversion) -- no bespoke float format involved.

- **`bytes_per_element(tensor) -> u64` was generalized to `expected_storage_bytes(element_count, tensor) -> u64`**, since a flat "bytes per element" doesn't exist for block formats (a `Q4_K` element's cost is `144/256` bytes, not an integer). The new function validates `element_count` divides evenly by the relevant format's block element count (32 for `Q8_0`, 256 for `Q4_K`/`Q5_K`) before computing total bytes, rather than silently truncating or rounding.

- **A real, discovered architectural blocker, surfaced rather than worked around**: `loaders/gguf`'s `weight_layout.rs` (`TransposingPayloadSource`) performs a real byte-level transpose of every 2D projection weight, computing row/column strides from `storage_dtype.descriptor().size_bytes()` -- a flat per-element byte width. This is correct for `F32`/`F16`/`BF16` (genuinely flat formats) and would silently corrupt a block-quantized tensor's structure if applied to its raw bytes (a block covers a fixed *run* of logical elements at a fixed byte size; slicing/swapping bytes as if each element had its own fixed width scrambles which bytes belong to which block entirely). Since most real quantized GGUF tensors *are* projections (norms typically stay unquantized in real quantized exports; token embedding is the one large tensor that is never transposed either way), this is not a corner case -- it affects nearly every quantized tensor a real file would carry. The correct fix is dequantize-then-transpose (operate on `F32` values, where the existing transpose logic is already correct), which requires `loaders/gguf` itself to dequantize before transposing inside its own payload-source wrapper -- meaning it would need its own copy of this change's dequantization logic (mirroring how `weight_layout.rs`/`derived_lm_head.rs` are already ported, not shared, between `loaders/huggingface` and `loaders/gguf`). Attempting this in the same change as the dequantization math itself was deliberately avoided: shipping working, tested dequantization now is real progress; rushing the loader-side sequencing fix in the same breath risked the exact "looks like it works but produces garbage" outcome that verification discipline exists to prevent.

## Risks / Trade-offs

- **A real quantized GGUF checkpoint still cannot be loaded end to end after this change** -- only the Model Loading primitive it will eventually need is now real and tested. This is explicitly communicated, not silently implied to be "done."
- **GPTQ/AWQ/BitsAndBytes remain entirely unaddressed.** These are large, separate undertakings (different math, different storage conventions, Hugging Face/Safetensors-shaped rather than GGUF-shaped) that this change does not reduce the scope of.
- **`get_scale_min_k4`'s bit-packing correctness rests on the hand-constructed unit tests' own correctness**, since no real quantized GGUF file was available to cross-check against during this change (unlike `wire-gguf-into-model-loading`'s unquantized numerical-parity tests, which had a real downloadable checkpoint). The tests were built by carefully hand-deriving expected values from the exact same formula being tested, then independently re-deriving them a second time during review to catch a real hand-calculation slip (an earlier version of the `Q4_K` test's own expected value for one sub-block was wrong -- it omitted the quantized nibble value as a multiplicative factor -- caught by the test failing against the (correct) implementation, not the other way around). A follow-up that wires quantized tensors through `loaders/gguf` should re-verify against a real quantized checkpoint once that blocker is resolved.
