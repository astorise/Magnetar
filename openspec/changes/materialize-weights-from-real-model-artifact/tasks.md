## 1. Generic bytes-to-HostTensor bridge

- [x] 1.1 Add `host_tensors_from_artifact_bytes(tensors: &[ModelTensorMetadata], bytes: &[u8]) -> Result<BTreeMap<String, HostTensor>, ModelLoadingError>` (exact error type/location a judgment call within `model_loading.rs`), depending only on `magnetar-runtime`'s own generic types. (Final signature gained a third parameter, `data_section_start: u64`, not anticipated when this task was written -- see 1.7's note and design.md for why.)
- [x] 1.2 Reject any tensor whose `storage_dtype` is not `ModelDType::F32` with a structured error, rather than reinterpreting bytes. (`ModelLoadingErrorCode::StorageDTypeUnsupported`.)
- [x] 1.3 Validate `size_bytes` matches the tensor's shape element count times 4 bytes before reading, using checked arithmetic (matching the discipline `formats/safetensors`/`formats/gguf` already apply on the parsing side).
- [x] 1.4 Validate the declared byte range fits within `bytes`'s actual length before slicing.
- [x] 1.5 Test: a well-formed tensor inventory + matching bytes produces the expected `HostTensor` map. (`host_tensors_from_artifact_bytes_reads_a_well_formed_tensor`.)
- [x] 1.6 Test: a non-F32 dtype is rejected structurally. (`host_tensors_from_artifact_bytes_rejects_non_f32_dtype`; plus `..._rejects_out_of_bounds_range` and `..._rejects_shape_size_mismatch` for the other structured-rejection paths.)
- [x] 1.7 Test: an out-of-bounds or size-mismatched range is rejected structurally, not panicking. **Real bug found and fixed via this task group's own tests, not anticipated by the original design:** the first implementation treated `offset_bytes` as an absolute file offset. It compiled and passed 1.5-1.7's own unit tests (which only ever exercised offset zero or an intentionally-absolute scenario) -- the bug was invisible until task group 3's parity test used a real multi-tensor file and got denormal/huge float values back for every tensor after the first. Root cause: every format parser's `offset_bytes` is relative to where the tensor-*data section* begins (after the header), not to byte zero of the whole file. Fixed by adding `data_section_start: u64` as an explicit third parameter the caller supplies (it already parsed the header to get here). New regression test `host_tensors_from_artifact_bytes_honors_nonzero_data_section_start` proves this specifically, with a synthetic "header" preceding the tensor bytes.

- [x] 3.2 Switch the production first-native weight-loading call site (`bind_qwen_fixture_weights`) from the in-memory `BTreeMap` bypass to the real-file path. **Deviates from this task's original wording, deliberately:** the existing digest-check gate stayed checked against `fixture.weights` (the in-memory map), *not* switched to the real file's digest -- because `check_weight_binding_rejects_tampered_artifact_bytes` (a real, pre-existing test) proves its tamper-detection guarantee by mutating `fixture.weights` at runtime, which a `include_bytes!`-embedded real file structurally cannot support (compiled-in bytes are immutable). Only the *materialization source* switched to the real file; the digest gate's job (catch a corrupted fixture object) is unchanged and still real, just no longer the same thing as "what gets written to Provider storage" -- those were quietly the same thing before this Change and are deliberately two separate checks now.
- [x] 3.3 Test: the full first-native E2E suite (generation, KV, weight-byte-change-alters-logits, tampered-digest-rejected, etc.) still passes unchanged with the new path as the only path. (1115/1115, up from 1108 before this Change's tests were added.)
- [ ] 3.4 Remove the now-dead in-memory-only code path once 3.3 is green, per this Change's own parity discipline (design.md). **Not done -- the premise turned out to be wrong, not deferred.** `e2e_fixture_weights()`'s in-memory path is not dead: it remains load-bearing for the digest-check gate (3.2's note) and for test helpers that deliberately need a *mutable* weight map to prove tamper-detection and weight-sensitivity (`check_weight_binding_rejects_tampered_artifact_bytes`, `check_weight_byte_change_alters_generated_logits`, both via `forward_logits_with_weights`/direct fixture mutation). Removing it would delete real, currently-passing test coverage for no benefit. Corrected here rather than forced through to match the original task wording.
