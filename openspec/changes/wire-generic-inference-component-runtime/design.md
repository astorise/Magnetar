## Context

The Tachyon integration audit's three P0 findings (MAG-01: the adapter is Qwen/HuggingFace-specific despite its generic name; MAG-02: the supplied Component WASM is not the real execution authority; MAG-03: Component trust is conflated with model trust) all trace back to one root cause investigated before any code was written: `magnetar-runtime` has never had a genuinely generic "run an arbitrary Component" execution path. Even the "real" WASM-invoking path (`run_first_native_generation`) is hardcoded to the literal model reference `"qwen-test"`, backed by a single process-wide `OnceLock<ComponentArtifactPackage>` (`QWEN_COMPONENT_ARTIFACT`) stamped with one constant digest (`QWEN_REAL_COMPONENT_DIGEST`). `inference-components::LoadedInferenceComponent::load` already calls `register_qwen_component_artifact` with whatever bytes a caller supplies -- but those bytes are only ever *used* later, inside `ProductionQwenLoadedModel::generate`'s call chain (`first_native_component_graphs_for_prompt` -> `build_first_native_graphs_from_real_qwen_component` -> `qwen_real_component_runtime`), which reads back the same single global slot and only accepts bytes matching the one hardcoded digest. A genuinely different Component would fail there, not at `load()` time -- a real, hard-to-notice failure mode that this session verified by tracing the actual call chain rather than assuming.

## Goals / Non-Goals

**Goals (this change, Phase A):**
- A caller can register an arbitrary Component artifact, trusted by its own `ComponentTrustStore`, keyed by the artifact's own real (`sha256`) digest.
- Multiple distinct Components can be registered and remain usable concurrently in one process.
- Reuse the existing, already-generic graph-production logic (`build_first_native_graphs_for_config`'s body) rather than duplicating it.
- Zero behavior change to the existing Qwen singleton path -- every existing test keeps passing unmodified.

**Non-Goals (deferred to later phases):**
- Wiring `inference-components::LoadedInferenceComponent` to actually use this registry instead of `register_qwen_component_artifact`/`ProductionQwenLoadedModel` (closing MAG-02 for real). This change makes the generic mechanism exist and proves it correct; a follow-up phase threads it through the Tachyon-facing adapter.
- `ArtifactTrustPolicy` gaining a real, separate `ComponentTrustStore` field distinct from its `ModelTrustStore` (MAG-03). That is `inference-components`' own concern, addressed alongside the wiring above.
- Pluggable model-format ingestion (HuggingFace vs. GGUF vs. others) for MAG-01's format-agnosticism -- a separate concern from Component *execution* genericity, which is this change's whole scope.
- Any change to `E2eRuntimeModelExecutionEngine`/`execute_generation_step`'s own dispatch (still hardcoded to the Qwen singleton) -- a real Component-per-instance generation loop needs `ProductionQwenLoadedModel` (or its replacement) to carry and thread through a specific registered digest, which is exactly the follow-up phase's job.

## Decisions

- **Purely additive: the existing Qwen singleton (`qwen_real_component_runtime`, `QWEN_COMPONENT_ARTIFACT`, `register_qwen_component_artifact`) is untouched.** Investigated first: this path backs a very large existing test suite (dozens of `e2e_qwen_component_*` tests) with exact timing/caching assumptions (`OnceLock`, compiled once per process). Modifying it to be generic in place would risk that whole suite for no benefit an entirely new, parallel mechanism doesn't already provide more safely.
- **Keyed by the artifact's own real digest (`ComponentDigest::sha256(&component_bytes)`), computed by the registration function itself -- never a caller-supplied claim taken on faith, and never a hardcoded constant.** This is the direct fix for the audit's core finding: trust and identity both now derive from the actual bytes and the caller's own `ComponentTrustStore`, not from a value baked into `magnetar-runtime` at compile time. The digest doubles as the registry's lookup key and the caller's handle -- no separate identifier needs inventing.
- **Graph production itself needed no change.** Investigated first (Explore agent + direct code reading): `build_first_native_graphs_for_config`'s body was already fully parameterized by `config: &QwenConfig`/`identity: &ModelComponentIdentity` -- nothing about walking the WIT `graph-builder`/`model-config` host-capability protocol was ever specific to which compiled Component binary was being driven. Extracting that body into `build_first_native_graphs_with_runtime(manager, capability, model_config_capability, definition, config, identity, prompt_token_count)` and having both the old singleton path and the new generic path call it means the two paths share one implementation, not two that could silently drift apart.
- **Verification compares the new path's output against the pre-existing path's output for the identical real Component bytes** (`build_first_native_graphs_from_named_component_matches_the_real_qwen_component_path`, using the same checked-in `qwen-real.component.wasm` fixture both paths already use in tests) -- not just "does not crash" or "produces some graph." Asserting equal operator-sequence hashes (not just node counts) is a strong proof the generic path reaches the exact same real behavior via a completely different registration/lookup mechanism.

## Risks / Trade-offs

- **Multi-Component coexistence is verified structurally, not end-to-end with two real, distinct Components.** `REGISTERED_COMPONENT_RUNTIMES` is a `BTreeMap` keyed by digest with `.entry().or_insert_with(..)` insertion, which never evicts an existing entry -- true by construction and by reading the code -- but this session's only checked-in Component fixture implementing the real `model-component-graph-producer` world is the single `qwen-real.component.wasm` used throughout. Proving two *distinct* real Components coexist and both produce correct graphs (closer to MAG-07's spirit) needs a second fixture Component authored against the same WIT world, deferred to the follow-up phase alongside the `inference-components` wiring, where real distinct fixtures are more naturally available.
- **Two structurally similar registries now exist side by side** (the Qwen singleton and this generic one) until a future phase decides whether/how to unify them. Accepted: unifying now would touch the heavily-tested singleton path for a benefit (avoiding ~150 lines of duplicated-but-shared-via-extraction logic) that does not outweigh the regression risk today.
- **`inference-components` still does not use this.** The audit's P0s remain open until the follow-up phase wires it in -- this change is a verified, real prerequisite, not the fix itself, mirroring this session's established pattern of landing a verified capability before the change that wires it into production use.
