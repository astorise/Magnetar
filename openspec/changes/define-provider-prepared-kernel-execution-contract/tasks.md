## 3. Multi-output Kernel dispatch

**Mostly not attempted (only 3.1 closed) -- a real scope gap found while investigating, corrected here rather than left silently unimplemented.** `KernelResult.updated_resources: Vec<TensorResourceDescriptor>` already *can* hold multiple entries structurally (confirmed and closed as task 3.1), but every one of Reference CPU's actual Kernel implementations (`run_invocation`'s `match name { "matmul" => ..., "embedding" => ..., ... }`) computes exactly one `HostTensor` and calls `store_output(invocation, 0, output)` exactly once -- there is no real Qwen operator that produces more than one output today, the same fact `reach-architecture-freeze-1`'s tasks 5.4/5.5 already found. Making `execute_qwen_graph_nodes` resolve `node.outputs` plural (task 3.3 as originally written here) is not reachable without *also* changing `dispatch_reference_cpu_operator`'s single `output: (TensorResourceId, TensorDescriptor)` parameter and single `HostTensor` return to plural, which ripples into every `dispatch_qwen_*` function (`dispatch_qwen_matmul`, `_unary`, `_binary_same_shape`, `_rmsnorm`, `_rope_per_head`, `_attention`, `_logits_projection`) -- exactly the "migrating every `dispatch_qwen_*` call site" work this Change's own `design.md` Non-Goals excluded. Building this without a real multi-output Kernel to validate against would mean inventing a synthetic one purely to exercise unused plumbing, the same trade-off `reach-architecture-freeze-1` already declined for the identical reason.

## 5. Migrate the generic per-node transport

**Not attempted -- found to be low-value without a second real Provider to validate against, not merely deferred by oversight.** Every current Kernel *computation* (`dispatch_qwen_matmul`, `rmsnorm`, `rope_per_head`, attention, ...) is Reference CPU's own Rust code operating on `HostTensor.data: Vec<f32>` directly, and stays that way regardless of this Change -- a device-resident Provider would have its *own* Kernel implementations operating on its own buffers, never routed through `dispatch_reference_cpu_operator` at all. Given that, wrapping `execute_qwen_graph_nodes`'s read/write calls in `TensorValue::Host(...)` and immediately unwrapping via `into_host` right before handing values to `dispatch_reference_cpu_operator` (which still requires raw `HostTensor` to compute) would change zero behavior today -- Reference CPU is the only real Provider, and it never produces `Opaque`. This migration's actual value is proven by group 4's tests already: the contract exists and a non-host-visible implementation can satisfy it. Wiring the generic executor through it for real is worth doing once there is a second real (not synthetic-test-only) Provider whose behavior would actually differ -- the same "don't force plumbing nothing yet exercises" judgment `reach-architecture-freeze-1` used for its own 5.4-5.6.
