## Why

An external readiness audit of the CUDA Provider effort (`docs/audits/cuda-provider-intermediate-audit-2026-09-05.md`) found two Core defects that block any non-Reference-CPU Provider from being used in Magnetar's real first-native inference path, independent of how complete that Provider's own kernels are. Both were confirmed by direct code inspection, not just the audit's own reading:

1. `WeightMaterializationTransaction::begin()` and `KvUpdateTransaction::begin()` (`magnetar-runtime/src/first_native_runtime.rs`) hardcode `ProviderBinding::new(REFERENCE_CPU_PROVIDER_NAME)` instead of reading the Provider/Device binding that Runtime already resolved and validated for the Model Instance (`ModelInstanceDefinition.placement.provider`/`.device`, cross-validated against the prepared plan in `Runtime::create_model_instance`). This directly violates `runtime` spec's existing "Runtime Treats Reference CPU As Normal Provider" requirement ("Runtime SHALL route Reference CPU execution through Provider, Kernel Registry... Runtime SHALL not use Reference CPU fallback silently"): today weight materialization and KV commit silently *do* force Reference CPU regardless of what was actually resolved. `providers/cuda`'s `CudaExecutor` already exists as a second, differently-named, fully `ProviderExecutionApi`-conformant Provider in the workspace with no path to reach either transaction because of this.
2. `ProviderExecutionApi`'s `TensorValue` mutation methods have an inconsistent, incomplete error channel: `write_tensor_value` returns bare `()` (no error channel at all — confirmed a no-op default and confirmed `ReferenceCpuExecutor`'s own implementation silently discards the `Result` from its inner `write_tensor` call), and `write_tensor_value_admitted` returns `Result<(), MemoryError>`, which can only express a Memory Manager admission failure, never a genuine Provider-native write failure (a CUDA H2D copy failing after admission succeeded, a lost context, an async error surfaced at sync time). The sibling `HostTensor`-typed pair (`write_tensor`/manual admit-then-write) already solved this exact problem via `ProviderExecutionErrorCode::MaterializationFailed` and an established admit-then-write-with-rollback pattern (`WeightMaterializationTransaction::stage_weight`, `promote_pending_kv_layer_role`), regression-tested by `stage_weight_propagates_and_rolls_back_on_provider_write_failure`. No equivalent test exists for the `TensorValue` path today because no real failure can currently reach it — both existing implementations back it with an infallible in-memory map.

Fixing both now — before investing further in CUDA-specific kernel or device-memory work — avoids building that work against a Core contract two independent reviews (the audit, and this proposal's own code-level confirmation) already know is wrong, and would otherwise force a rewrite once a genuinely device-resident Provider needs either path to work.

## What Changes

- `WeightMaterializationTransaction::begin()` resolves its `ProviderBinding` from the target Model Instance's `placement.provider` (falling back to Reference CPU only when placement leaves it unset, matching current default behavior for existing CPU-only callers) instead of the hardcoded constant. Requires threading `instance: &ModelInstanceId` (or the resolved binding) into `begin()`; the caller (`materialize_model_instance_weights`) already has it one frame up.
- `KvUpdateTransaction::begin()` resolves its `ProviderBinding` the same way `execute_qwen_graph` already correctly does (`prepared_plan.node_bindings.first().map(|binding| binding.provider.clone())`), instead of the hardcoded constant. Requires threading the model-instance id (or resolved binding) from `commit_generation_step` through `promote_pending_kv_resources` into `begin()`. `discard_pending_kv_state`'s equivalent hardcoding on the abort/cancel path is fixed identically for symmetry.
- `ProviderExecutionApi::write_tensor_value` changes from `fn write_tensor_value(&self, id: TensorResourceId, value: TensorValue)` to `fn write_tensor_value(&self, id: TensorResourceId, value: TensorValue) -> Result<(), ProviderExecutionError>` (default `Ok(())`, matching `write_tensor`'s existing shape and `MaterializationFailed` category). **BREAKING** for any existing implementor of this trait method (in-tree: `ReferenceCpuExecutor`, `providers/cpu`'s and `providers/cuda`'s executors, test mocks in `first_native_runtime/tests.rs` and `tests.rs`) — all updated in this change.
- `ProviderExecutionApi::write_tensor_value_admitted` changes to distinguish a Memory Manager admission failure from a genuine Provider-native write failure, following the existing admit-then-write-with-rollback precedent rather than conflating both into one `MemoryError`-typed result. **BREAKING** for the same set of implementors, updated in this change.
- `execute_qwen_graph_nodes`'s three call sites (graph input bindings, pending KV resource, node output edge) updated to handle the new, distinguishable error shape, matching `stage_weight`'s existing rollback discipline.
- New regression test mirroring `stage_weight_propagates_and_rolls_back_on_provider_write_failure`, but for the `TensorValue` path: a mock Provider that fails a `TensorValue` write after successful admission, asserting the error is reported and the just-admitted allocation is released, not leaked.

**Explicit non-goals** (left for later, separate work — not part of closing these two P0s):
- Making `RuntimeModelExecutionEngine`/`Runtime::model_execution_engine` non-`pub(crate)` so an external embedder could register a non-CPU model-execution engine. `KvUpdateTransaction`'s current blast radius stays confined to this crate's internal Qwen-fixture wiring; this change makes that internal wiring provider-correct, it does not make it externally pluggable.
- Any device-resident (`TensorValue::Opaque`) implementation, allocation table, or actual CUDA usage of the now-fixed paths. This change only removes the Core blockers; proving a real device-resident datapath (the audit's Gate 2–4) is separate follow-up work.
- Redesigning `write_tensor_admitted`'s (the `HostTensor`-typed sibling) own admission signature — it is not broken in the way `write_tensor_value_admitted` is, and `stage_weight` already gets its rollback discipline by composing `MemoryManager::allocate` and `write_tensor` manually rather than through that combined method.
- Sizing semantics for admitting a `TensorValue::Opaque` write (no byte length is derivable from the value itself). Every call site this change touches only ever produces `TensorValue::Host` today; solving `Opaque` admission sizing is part of the deferred device-residency work above.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `runtime`: "Runtime Treats Reference CPU As Normal Provider" requirement gains explicit scenarios covering weight materialization and KV commit specifically (today's requirement is general; the violation was in these two concrete transactions).
- `provider`: the `TensorValue` mutation requirements (`write_tensor_value`/`write_tensor_value_admitted`) are amended to require a real, structured Provider-execution error channel, consistent with the already-normative `write_tensor` requirement.

## Impact

- `magnetar-runtime/src/first_native_runtime.rs`: `WeightMaterializationTransaction::begin()`, `materialize_model_instance_weights`, `KvUpdateTransaction::begin()`, `commit_generation_step`, `promote_pending_kv_resources`, `discard_pending_kv_state`, `execute_qwen_graph_nodes`'s three `write_tensor_value_admitted` call sites.
- `magnetar-runtime/src/provider.rs`: `ProviderExecutionApi` trait (`write_tensor_value`, `write_tensor_value_admitted` signatures and default implementations).
- `magnetar-runtime/src/reference_cpu.rs`: `ReferenceCpuExecutor`'s implementations of both methods.
- `magnetar-runtime/src/first_native_runtime/tests.rs` and `magnetar-runtime/src/tests.rs`: mock `ProviderExecutionApi` implementors (`FailableProviderExecutionApi` and others) updated to the new signatures; new regression test for `TensorValue` write-failure rollback.
- External submodules with their own `ProviderExecutionApi` implementations — `providers/cpu` (`magnetar-provider-cpu`) and `providers/cuda` (`magnetar-provider-cuda`) — need their `write_tensor_value`/`write_tensor_value_admitted` implementations updated to the new signatures as a follow-up in each submodule's own repository once this Core change lands and its pin advances; not part of this change's own diff (per `externalize-runtime-extension-modules`, the Core has zero compile-time dependency on either).
- No WIT/Component-facing contract changes: both fixes are internal to the native Runtime-to-Provider boundary, never exposed to portable Components.
