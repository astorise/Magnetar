## Baseline and ownership

The runtime already has Reference CPU/CUDA execution, real Qwen production ingestion, a real Llama Component, model/graph/plan/affinity/memory/KV/batching contracts and cryptographic artifact validation. These changes operationalize and extend that foundation; they do not recreate it. Direct low-precision/quantized compute, production serving/cache loops and alternative Provider compute need profile-specific evidence. Current WGPU has real discovery/add; ROCm/NPU are discovery-only and native Metal is a placeholder. Explicit delta replacements remove those restrictions only in their qualified future profiles. G05 promotes descriptive placement into an enforced production plan while retaining diagnostics and the single-Device baseline. C01 resolves the current distinction between cross-Provider candidate enumeration and hard-affinity-safe production selection.

- Runtime owns local resolution, graph/plan validation, MemoryManager, resource affinity, sessions/KV, admission, scheduling and redacted diagnostics.
- Providers own native kernels/compiler artifacts, Device allocations, copies, capture, streams/events and timing; Components never see native handles or choose hardware.
- Components/loaders own model-family semantics, portable graph/state topology, tokenization and authorized artifact ingestion.
- The external Optimization Plane owns bounded campaigns and signed recommendations; Runtime retains validation and promotion.
- Tachyon owns optional inter-node placement, transport and global routing. Its repository was not inspected; all proposed interfaces require an independent audit and agreement. Magnetar remains standalone.

## Waves and critical path

| Wave | Indicative window | Exit evidence |
|---|---|---|
| V0 Reference | November-December 2026 | Real-model CPU/CUDA comparable tokens/logits, generation CLI, historical performance/memory/I/O/quality |
| V1 Precision/kernels | January-March 2027 | Native F16/BF16 plus one direct quantized profile, no mandatory whole-model F32 expansion, numeric and measured benefit |
| V2 Compilation/dispatch | March-June 2027 | Qualified graph passes, cached plans and CUDA replay reduce launches/synchronization with fallback |
| V3 Residency/KV | May-August 2027 | Budgeted SSD/RAM/VRAM weights, paged KV and safe prefix reuse under concurrency |
| V4 Serving | July-October 2027 | Real batching, chunked prefill and async scheduling improve throughput/latency at admitted load |
| V5 Advanced models | September 2027-January 2028 | Real dense/MoE/draft/adapter/specialized model profiles with logits and downstream quality |
| V6 Portability/distribution | December 2027-April 2028 | Real alternative compute, enforced local multi-GPU and explicit state transfer; multi-node P/D only after Tachyon audit |

Waves overlap. The critical path is evidence/production CLI → native precision/direct quantization → residency/KV/preparation/fusion → batching/chunked prefill/async/adaptation → multiple models/MoE/speculation/multiple Devices → explicit state transfer and optional distributed P/D. Hardware experiments can start independently but cannot bypass prerequisites for qualification. Dates and theoretical gains are hypotheses, not delivery promises.

Four workstreams retain the source allocation: kernels/numerics (B01-B10, C03-C07), memory/residency (D01-D11, F02/F05), serving/scheduler (A05, E01-E10), hardware/distribution (G01-G10). A01-A04/A06/A08/C01/C09 form the shared qualification platform. P0/P1 establish the baseline; P2/P3 require bounded experiments and benefit evidence. P3 is conditional, never a delivery commitment.

## Qualification, rollout and stop criteria

The qualification change contains normative shared gates. Initial comparisons use pinned Qwen2.5-0.5B-Instruct, Reference CPU and real CUDA; ARM NEON, AMD, Apple, NPU and multi-GPU profiles require actual accessible machines. Extend to a verified quantized checkpoint, a non-Qwen dense family, then MoE after correct routing exists. Record target hardware (including the historical RTX 3070 Ti Laptop as a candidate, not an available resource), driver, code and Provider SHAs, model revision/weight digests, flags and budgets.

Use concurrency 1/4/16/32 and context 512/4096/16384 with 128-512 generated tokens only within checkpoint/backend/memory limits. Keep cold and warm results separate; aim for at least five post-warmup repeats, justify expensive exceptions, retain raw samples, medians/dispersion/uncertainty and control run order/interference. Record TTFT, TPOT/ITL p50/p95/p99, aggregate and per-request tokens/s, actual utilization, kernel and host launch time, RSS/VRAM peaks, SSD/PCIe bytes/token, real demand hits versus prefetch, saved prefill, fragmentation/OOM, warmup/compile cost and energy only with valid telemetry. Compare at equal total memory budgets and keep external-engine comparisons separate from gains against Magnetar v1.0.

Numerical gates declare operator/dtype tolerances, logit comparisons and pinned downstream quality thresholds; seeded/pinned mode disables unqualified adaptation/nondeterminism. Every optimization needs an explicit disable path, safe fallback or Unsupported response and generation-aware rollback. Validate cancellation, concurrency, error propagation, memory pressure, tampered artifacts and incompatible KV reuse. Keep Rust/WIT/OpenSpec/conformance and third-party license/SBOM/signature/reproducibility gates. Never promote a below-noise speedup, an unexplained quality/p95 regression or a claim based only on discovery, fixtures or contracts.

Stop or defer when actual precision/quality fails, I/O dominates without a demonstrated useful target, captures/prefetch violate budgets, lifecycle publication races exist, QoS starves peers, native dependencies break portability, or distributed transfer costs exceed benefit. No blanket interactive-speed, memory-ratio or release-version promise follows from these proposals.

## Decisions deliberately left profile scoped

1. Initial accessible hardware and whether the objective is single-user latency, workstation concurrency or serving throughput.
2. Exact second dense, MoE, MLA/KDA and optional multimodal checkpoints, licenses and expected operator coverage.
3. Per-dtype/per-layer numerical error, downstream-quality tolerances and QoS/memory/energy acceptance thresholds.
4. Real access to AMD, macOS, Intel/Qualcomm NPU and multiple GPUs/interconnects; missing machines stay skipped.
5. The exact versioned WIT/API additions needed after reusing existing contracts, with negotiation and migration; none is silently frozen by this planning work.
6. Tachyon ownership, transport authentication/encryption, state replay policy, producer fencing and multi-node audit outcomes.
7. Staffing and scheduling across the four streams. No team allocation or release calendar is established here.

## Success criteria and version interpretation

The qualification delta encodes the source's proposed 2.x goals: native half plus direct quantization, real multi-token Device-resident execution where supported, concurrent paged-KV/prefix serving, evidence-based selection with rollback/pinned mode and reproducible v1.0 comparisons. A second real compute Provider is conditional on hardware and remains an explicit limitation otherwise. Proposed 3.x additions require robust multi-GPU, qualified MoE and versioned state mobility with independently audited multi-node Tachyon proof. These are profile-specific evidence goals, not promises of a major version, blanket model support or measured performance in this authoring session.
